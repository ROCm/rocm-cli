# Architecture

This is the living module map for rocm-cli: a contributor-facing reference to where things live and why, updated in the same PR as the code it documents. It documents the current structure, not the decisions or debates that produced it.

> Before relying on any entry below, verify current file and function boundaries directly (e.g. `grep`) rather than trusting this doc's wording. Module boundaries shift as the codebase grows, and a stale-but-plausible-looking note is worse than an explicit prompt to check. A citation of a specific file in this document is a relative markdown link at its first mention in a table row or bullet; later mentions of the same file in that row or bullet are bare, and so are generic mentions (such as `main.rs`, `lib.rs`, `mod.rs` or the workspace `Cargo.toml`), runtime or generated files (such as `config.json` or `report.json`) and files that are not tracked in this repository. The links are checked offline by [lychee](https://github.com/lycheeverse/lychee) in CI (the `docs-links` job, config in [`lychee.toml`](../lychee.toml)), so a moved or deleted file fails CI immediately and names the broken link. That check does not verify that the surrounding prose is still accurate; the caution above still applies to everything but link resolution.

A second check runs the other way: `cargo xtask check-architecture-doc` ([`architecture_doc.rs`](../xtask/src/architecture_doc.rs)) fails when a production source file, meaning a `.rs` file under `apps/*/src`, `crates/*/src` or `engines/*/src`, has no link in this document, so a new module cannot land without a link here, normally its row. It covers the repository's own tooling and test harness the same way: every `.rs` file under `xtask/src`, `tests/e2e-cucumber/src` and `tests/e2e-cucumber/tests` needs a link too. Only a link that renders as one counts: a path inside an HTML comment, a code block or a code span does not, and neither does a malformed link (one missing its `[` or `)`, or with an escaped bracket), an image, or the outer brackets of a link that contains another link. Write the row's file cell as an inline `[text](path)` link with its text on one line; `<path>` delimiters around the destination are accepted, but reference-style links, a `?query` suffix and root-relative paths are not. `build.rs` files and the `tests/` and `examples/` trees of the product crates are out of scope. It runs in the `clippy` CI job and in the `architecture-doc` prek hook, at commit and at push. Test-only helpers (`test_support.rs`, `test_env.rs`, `proptests.rs`, `*_proptests.rs`, `*_props.rs`, `*_properties.rs`) may have a row but need none in a production crate; in the `xtask` and `tests/e2e-cucumber` trees every file needs one, whatever its name. There is no exemption list: a file in scope with no link fails the check. The check reads no prose, so keeping a row's description true is up to the change that edits the file.

## Module organization convention

New subcommands and subsystems default to their own file from day one. They should not grow inside `main.rs`/`lib.rs` waiting for a future extraction pass. Two extraction patterns exist in the codebase; use whichever fits. The Class column of the module map below records which one a file was extracted under, where that is recorded.

- **Full domain extraction** (`domain`): a subsystem's domain implementation moves into its own file that owns its own types, not just relocated functions. Every `apps/rocm` module is a private `mod x;` regardless of pattern, so privacy does not tell the two patterns apart. Domain-extracted modules are typically reached through qualified paths (e.g. `comfyui::run(...)`), and so are mechanically relocated modules that own no types (e.g. [`endpoint_keys.rs`](../apps/rocm/src/endpoint_keys.rs), [`logging.rs`](../apps/rocm/src/logging.rs)). The exception, reached unqualified through `use crate::x::{...}` re-imports that match the dispatch call sites' pre-extraction form, is limited to the clusters that moved as a dispatch-adjacent group; the block of `use crate::x::{...}` re-imports near the top of [`main.rs`](../apps/rocm/src/main.rs) is the current list of modules reached that way. Where a subsystem has a dedicated clap subcommand, its command enum usually lives in [`cli.rs`](../apps/rocm/src/cli.rs) with the rest of the `Cli`/`Command` definition (e.g. `ComfyuiCommand`, `RuntimesCommand`), the way [`apps/rocmd`](../apps/rocmd/src/cli.rs) keeps its command tree in a `cli.rs` of its own. The dispatch function, the match over that tree, does not stay with the enum: `comfyui::run` lives in [`comfyui.rs`](../apps/rocm/src/comfyui.rs), and `engines()` and `runtimes()` live in [`engines_cmd.rs`](../apps/rocm/src/engines_cmd.rs) and [`runtimes_cmd.rs`](../apps/rocm/src/runtimes_cmd.rs). Only the top-level `dispatch()`, the match that sends each `Command` variant to its handler, stays in `main.rs`. [`bootstrap.rs`](../apps/rocm/src/bootstrap.rs) and [`remote/mod.rs`](../apps/rocm/src/remote/mod.rs) own their command enum as well as their dispatch. Not every domain-extracted module has a command enum at all ([`providers.rs`](../apps/rocm/src/providers.rs) has none). In library crates (`crates/rocm-core`) a new subsystem is `pub mod x;` plus a `pub use x::{...};` re-export, since it is part of the crate's public API. This is the default for new subsystems. Examples: [`therock.rs`](../apps/rocm/src/therock.rs) (TheRock SDK install orchestration, with its other clusters in `therock/` child modules and no command enum of its own), [`comfyui.rs`](../apps/rocm/src/comfyui.rs) and [`providers.rs`](../apps/rocm/src/providers.rs); `crates/rocm-core`'s [`diagnose.rs`](../crates/rocm-core/src/diagnose.rs) and [`examine.rs`](../crates/rocm-core/src/examine.rs).
- **Mechanical relocation** (`relocation`): a `pub(crate) fn` moves out verbatim, with shared types and config staying at the crate root and reached via `crate::`. Used for dispatch-adjacent clusters where a minimal, easy-to-review diff matters more than full extraction. Example: [`update_cmd.rs`](../apps/rocm/src/update_cmd.rs). When the cluster is large enough to own types, they move with it instead of staying in `main.rs` (e.g. [`engines_cmd.rs`](../apps/rocm/src/engines_cmd.rs), [`driver_install.rs`](../apps/rocm/src/driver_install.rs), [`serve_cmd.rs`](../apps/rocm/src/serve_cmd.rs)). It is still mechanical relocation rather than domain extraction, because the call sites kept their pre-extraction unqualified re-import form when the code moved. Where a subcommand's dispatch function lives is not what decides it: a domain-extraction module can host its own (see `comfyui::run` above).

Moving a `proptest!` block to another file leaves its saved failure cases behind unless they are carried over: proptest keys them by the test's source file (`<crate>/src/<path>.rs` reads `<crate>/proptest-regressions/<path>.txt`, where `src/` is the directory holding `main.rs` or `lib.rs`) and does not warn when the file stops matching. Carry them in the same commit, and how depends on how much moved. When every property test of the file moves and the new file has no regression file yet, `git mv` the old one to the name the new file needs. When only some move, the tests left behind still read the old file, so keep it, and copy the saved cases to the new file's regression file (appending to it when it already exists, so its own cases stay). An `xtask` test fails the build on a regression file no test reads; it cannot notice a regression file that was moved away from tests that still need it, so check a split's diff for that. See [Property tests](testing.md#property-tests).

A flat size limit backs this convention: `cargo xtask check-module-size` ([`module_size.rs`](../xtask/src/module_size.rs)) fails when any source file has more than 1,500 production lines, and there is one limit for every file, with no per-file ceilings, baseline or exemption. Production lines exclude test-gated items (inline `#[cfg(test)]` modules and the like), and test-only files are not source files; the exact definition is at the top of that file. The check blocks merges: the `clippy` CI job, a required check that also runs on merge-queue runs, fails when any file is over the limit, so a file over it has to be split before anything else merges. The `cargo-module-size` pre-commit hook is the local mirror of that step: it runs the same check and refuses a commit that stages Rust source while a file is over the limit, without rewriting or restaging anything. It measures the working tree, so it also fails when a Rust file under a crate's `src/` is declared by no `mod`, even an untracked scratch file (the error says to declare or delete it). Because it runs at pre-commit and not pre-push, it also refuses the intermediate commits when an over-limit file is split across several commits, where CI only sees the final state: do the split in one commit, or commit the intermediate steps with `SKIP=cargo-module-size git commit ...`. It runs only for contributors who installed the hooks, so CI stays the authority. A PR that would push a file past 1,500 production lines splits it in the same change (a pure move, the tests moving with the code, this document updated in the same PR); raising the limit or exempting a file is not an option for a feature PR. `too_many_lines = "allow"` in the workspace `Cargo.toml` stays a deliberate function-level choice; this gate is about files.

## Module map

Scoped to the crates that make up the shipped CLI, daemon, dashboard and engine surface, plus `crates/e2e-report`, `xtask` and `tests/e2e-cucumber`. `crates/e2e-report` is HTML and markdown reporting consumed only by `xtask` and `tests/e2e-cucumber`; those two are the repository's tooling and test harness, and `check-architecture-doc` checks that every file in them has a row.

Each crate has a table with a row per source file (`rocm-dash-tui` and `tests/e2e-cucumber` have one table per directory), sorted by path with the crate roots (`main.rs`, `lib.rs`) first and a directory's `mod.rs` first within its directory. The Class column records how a file came to be, not a rule a new file is judged by: `domain` (full domain extraction or a child module of one, the default for a new subsystem), `relocation` (mechanical relocation) and `flat` (everything else: crate roots, files with no extraction pattern recorded, and test-only support). The `xtask` and `tests/e2e-cucumber` tables are `flat` throughout, since they hold tooling and test files rather than extracted subsystems, so the column carries no information for them. Under each table, **Boundaries** lists some of the facts a row cannot show, such as layering and leaf modules, deliberate privacy and shared sources of truth. It is a selection, not an inventory; the source files carry the rest.

### `apps/rocm` — main CLI binary

Boundaries:

**Module layout**

- Every module is a private `mod` in [`main.rs`](../apps/rocm/src/main.rs). Full-domain modules are typically reached by qualified path (`comfyui::run`); the dispatch-adjacent relocated clusters are reached unqualified through the `use crate::x::{...}` re-import block near the top of `main.rs`, which lists them.
- `engine_inventory` in [`main.rs`](../apps/rocm/src/main.rs) is the table of built-in engine ids. It, `status_for_readiness`, `device_policy_name` and `ROLLBACK_RECOVERY_HINT` stay at the crate root because modules across the crate use them.
- Most clap enums live in [`cli.rs`](../apps/rocm/src/cli.rs) and handlers in their domain or `*_cmd.rs` module; [`bootstrap.rs`](../apps/rocm/src/bootstrap.rs) and [`remote/mod.rs`](../apps/rocm/src/remote/mod.rs) are the exceptions that own their enum and dispatch fn. Declaration order in [`cli.rs`](../apps/rocm/src/cli.rs) sets the order of every nested `--help` list.

**Chat and the freeform planner**

- [`chat/turn.rs`](../apps/rocm/src/chat/turn.rs) is the top of the `chat/` call graph; `intent`, `mcp_bridge` and `summaries` never call back into it.
- `chat` calls the freeform planner, so [`freeform_planner.rs`](../apps/rocm/src/freeform_planner.rs), [`prompt_text.rs`](../apps/rocm/src/prompt_text.rs), [`rocm_argv.rs`](../apps/rocm/src/rocm_argv.rs) and [`tool_policy.rs`](../apps/rocm/src/tool_policy.rs) must not import `chat`; [`chat_import_contract.rs`](../xtask/src/chat_import_contract.rs) enforces it.
- [`chat_cmd.rs`](../apps/rocm/src/chat_cmd.rs) stays outside [`chat.rs`](../apps/rocm/src/chat.rs) because it calls both [`chat.rs`](../apps/rocm/src/chat.rs) and [`dash.rs`](../apps/rocm/src/dash.rs), and [`dash.rs`](../apps/rocm/src/dash.rs) already calls [`chat.rs`](../apps/rocm/src/chat.rs).
- A freeform plan is built once and that value is executed, because a cloud planner provider may not be deterministic; `plan_freeform_request_with_context` does the same for the `natural_language_plan` tool.
- `validate_serve_command_safety` in [`tool_policy.rs`](../apps/rocm/src/tool_policy.rs) holds the four rules a model-proposed `serve` must pass (no public bind, no CPU device, a loopback host, `--managed` without `--foreground`); the planner calls it and keeps no copy.

**Runtimes**

- [`runtime_registry.rs`](../apps/rocm/src/runtime_registry.rs) depends on neither [`therock.rs`](../apps/rocm/src/therock.rs) nor [`runtimes_cmd.rs`](../apps/rocm/src/runtimes_cmd.rs), and [`runtime_adopt.rs`](../apps/rocm/src/runtime_adopt.rs) and [`runtime_uninstall.rs`](../apps/rocm/src/runtime_uninstall.rs) do not depend on [`runtimes_cmd.rs`](../apps/rocm/src/runtimes_cmd.rs), which re-exports their names.
- [`engine_install_env.rs`](../apps/rocm/src/engine_install_env.rs) imports [`runtime_adopt.rs`](../apps/rocm/src/runtime_adopt.rs) and [`runtime_registry.rs`](../apps/rocm/src/runtime_registry.rs) directly: going through [`runtimes_cmd.rs`](../apps/rocm/src/runtimes_cmd.rs) would lead back to it via [`runtime_services.rs`](../apps/rocm/src/runtime_services.rs).
- [`runtime_install_finalize.rs`](../apps/rocm/src/runtime_install_finalize.rs) does not import [`engines_cmd.rs`](../apps/rocm/src/engines_cmd.rs). [`runtime_install_finalize/torch_alignment.rs`](../apps/rocm/src/runtime_install_finalize/torch_alignment.rs) is its child, not a sibling, because a sibling would form a cycle with the parent's device check.
- `select_single_ready_runtime` in [`runtime_adopt.rs`](../apps/rocm/src/runtime_adopt.rs) is the one ready-runtime rule for the engine paths and ComfyUI; every runtime registration goes through `write_runtime_manifest` in [`runtime_registry.rs`](../apps/rocm/src/runtime_registry.rs).
- The serde shapes of `InstalledRuntimeManifest` and `ActiveRuntimeMarker` are on-disk contracts.
- `PlannedPython` in [`therock/python.rs`](../apps/rocm/src/therock/python.rs) writes its `python_note:` text (`note` for an install preview, `update_note` for an update check) from the same decision the install branches on, so a note cannot name a version the install will not prepare.
- Whether an install root holds a payload is `rocm_core::install_root_has_payload`, and os-release is read only through `rocm_core::hardware_root::real_os_release`; a test in [`system_packages.rs`](../apps/rocm/src/system_packages.rs) fails when a source file of this binary calls `read_os_release(` or `identity_path_for_str` directly.

**Services and uninstall**

- `service_launch` does not import [`service_control.rs`](../apps/rocm/src/service_control.rs), which imports it (the Ctrl-C stop is passed into `run_attached_service`), and [`services_text.rs`](../apps/rocm/src/services_text.rs) does not call back into [`service_control.rs`](../apps/rocm/src/service_control.rs).
- [`background_helper.rs`](../apps/rocm/src/background_helper.rs) imports nothing from the service modules, so its helper note can be read without importing the spawner.
- [`uninstall.rs`](../apps/rocm/src/uninstall.rs) and [`uninstall_plan.rs`](../apps/rocm/src/uninstall_plan.rs) depend on each other; the plan half is separate because [`storage.rs`](../apps/rocm/src/storage.rs) shares it.
- [`service_launch/endpoint_auth.rs`](../apps/rocm/src/service_launch/endpoint_auth.rs)'s `ensure_public_bind_engine_supported` refuses a public bind with the managed Lemonade engine on Windows, because its endpoint API key cannot be enforced there; vLLM enforces its key on every platform, and a loopback bind needs none.

**Shared sources and contracts**

- [`service_hints.rs`](../apps/rocm/src/service_hints.rs) is the shared builder of the `rocm services stop|restart|remove <id> --yes` hint text, so the callers that use it cannot drift apart. Those callers are [`remote/mod.rs`](../apps/rocm/src/remote/mod.rs), [`serve_port.rs`](../apps/rocm/src/serve_port.rs), [`serve_summary.rs`](../apps/rocm/src/serve_summary.rs), [`service_control.rs`](../apps/rocm/src/service_control.rs), [`service_records.rs`](../apps/rocm/src/service_records.rs), [`services_cmd.rs`](../apps/rocm/src/services_cmd.rs), [`services_text.rs`](../apps/rocm/src/services_text.rs) and, under `service_launch/`, [`attach.rs`](../apps/rocm/src/service_launch/attach.rs) and [`spawn.rs`](../apps/rocm/src/service_launch/spawn.rs); the parent [`service_launch.rs`](../apps/rocm/src/service_launch.rs) does not call it.
- `DEFAULT_ENGINE_MARKER` in [`examine_report_text.rs`](../apps/rocm/src/examine_report_text.rs) is shared by both engine-inventory renderers and their legend line, so the rendered marker and the legend cannot drift apart.
- [`shell_quote.rs`](../apps/rocm/src/shell_quote.rs) is the CLI's quoter; `rocm-dash-tui` keeps a copy (`quote_display_arg`) because it may not depend on `rocm-core`, and a property test here holds the two equal.
- The local-model thinking rule [`providers/wire.rs`](../apps/rocm/src/providers/wire.rs) applies lives in `rocm-dash-core`'s [`chat_template.rs`](../crates/rocm-dash-core/src/chat_template.rs), because the dashboard's chat client must decide it identically.
- [`chat/turn.rs`](../apps/rocm/src/chat/turn.rs) compiles in [`SKILL.md`](../skills/rocm-cli-assistant/SKILL.md).
- `cargo xtask verify-pinned-keys` checks the metadata key in [`therock/fetch.rs`](../apps/rocm/src/therock/fetch.rs) by path.
- `ROCDXG_PINNED_DIGESTS` in [`driver_plan/rocdxg.rs`](../apps/rocm/src/driver_plan/rocdxg.rs) is the trust anchor of an unattended root install.
- `render_update_json` in [`therock/update.rs`](../apps/rocm/src/therock/update.rs) is the form the dashboard's update check parses.
- Saved property-test failures are keyed by the test's source file, so a moved property test takes its file in `apps/rocm/proptest-regressions/` along (see [Property tests](testing.md#property-tests)).

Boundaries:

- **Which binary runs what.** The daemon runs as `rocmd` or embedded in `rocm` (`rocm daemon`); `supervise` is `rocmd`'s alone and the hidden engine commands are `rocm`'s alone. A spawn of either takes its binary from [`daemon_host.rs`](../apps/rocmd/src/daemon_host.rs)'s `DaemonHost`, the one executable path these choices are made from.
- **The Anthropic proxy is not a daemon task.** [`anthropic_proxy.rs`](../apps/rocmd/src/anthropic_proxy.rs) is started by `rocm`'s `run_builtin_engine_serve_http` in [`engine_ipc.rs`](../apps/rocm/src/engine_ipc.rs), on a thread of the process that owns the engine, so it lives and dies with the service.
- **Shared subprocess capture.** [`common.rs`](../apps/rocmd/src/common.rs) only chooses the child's `ROCM_CLI_*_DIR` environment; the capture and spawn are [`command_capture.rs`](../crates/rocm-core/src/command_capture.rs) in `rocm-core`, shared with `rocm`'s chat tool bridge.
- **Supervised-record writes.** After a supervisor's first write, every write to its record goes through `update_supervised_record`, which is `pub(crate)` in [`supervise.rs`](../apps/rocmd/src/supervise.rs); [`watchers/server_recover.rs`](../apps/rocmd/src/watchers/server_recover.rs) calls it directly to stamp `last_restart_unix_ms` after a failed restart.
- **Watcher re-exports.** [`watchers.rs`](../apps/rocmd/src/watchers.rs) re-exports `stop_requested` and `find_recoverable_service` from [`server_recover.rs`](../apps/rocmd/src/watchers/server_recover.rs). [`supervise.rs`](../apps/rocmd/src/supervise.rs) imports `stop_requested` in production code, and `find_recoverable_service` is called by `watchers.rs` itself and by `supervise.rs`'s tests; so neither re-export is test-only.
- **Deliberate re-export.** [`lib.rs`](../apps/rocmd/src/lib.rs) exports `parse_args` because `apps/rocm`'s test-only [`advised_commands.rs`](../apps/rocm/src/advised_commands.rs) checks advised `rocmd` commands with it.
- **Layering.**
  - [`sandbox_tool.rs`](../apps/rocmd/src/sandbox_tool.rs) imports no other module of the crate, so modules that need the sandbox-tool vocabulary do not import [`cli.rs`](../apps/rocmd/src/cli.rs).
  - [`artifact_prefetch.rs`](../apps/rocmd/src/artifact_prefetch.rs) is called only by [`sandbox.rs`](../apps/rocmd/src/sandbox.rs) and does not import it back; it takes `SandboxToolArg` and `SandboxToolPolicy` from [`sandbox_tool.rs`](../apps/rocmd/src/sandbox_tool.rs).
  - A watcher child imports no sibling watcher module except [`watchers/policy.rs`](../apps/rocmd/src/watchers/policy.rs), and the thermal-protect watcher, which reads [`watchers/gpu_metrics.rs`](../apps/rocmd/src/watchers/gpu_metrics.rs)'s interval and thresholds.
  - `pending_proposal_exists` in [`watchers/policy.rs`](../apps/rocmd/src/watchers/policy.rs) is the one duplicate-proposal check the thermal-protect and server-recover handlers share.
- **Three watchers stay reviewed or read-only in contained mode.**
  - The `therock-update` watcher runs only the read-only `check_updates` sandbox tool and never applies an update.
  - The `driver-upgrade` watcher runs only the restricted read-only `driver_plan` tool and executes no driver command.
  - The `cache-warm` watcher queues a reviewed proposal even in contained mode, because an artifact download needs explicit source-policy approval.

Boundaries:

- **Crate-root primitives.** The helpers in [`lib.rs`](../crates/rocm-core/src/lib.rs) stay at the crate root on purpose: each is used from more than one module or crate, and no module's domain owns it. Single sources among them:

- **Module fronts and privacy.**

- **Failure catalog.**

  - The platform children of `diagnose/` do not import each other, and [`diagnose/catalog.rs`](../crates/rocm-core/src/diagnose/catalog.rs) is the only module that names every checker.
  - In `fix/`, the render and manifest modules read `RECIPES` from the catalog module, which reads neither.
- **Host probing.**
  - [`host_gpu.rs`](../crates/rocm-core/src/host_gpu.rs) and [`examine.rs`](../crates/rocm-core/src/examine.rs) are two separate stacks that read some facts twice (the Windows GPU query, the marketing-name table and the subprocess runners); [`host-probing.md`](host-probing.md) proposes which copy of each should survive. Three pairs are converged: the `PATH` lookup between the two stacks ([`probe_exec.rs`](../crates/rocm-core/src/probe_exec.rs)'s `which` is the only copy there; other modules walk `PATH` for their own purposes, for example `find_mpirun_path` in [`openmpi.rs`](../crates/rocm-core/src/openmpi.rs) and the executable search in [`runtime.rs`](../crates/rocm-core/src/runtime.rs)), the kernel release ([`host_gpu/os_facts.rs`](../crates/rocm-core/src/host_gpu/os_facts.rs)'s `detect_kernel_version` is now the only `uname -r` reader) and the CPU model ([`host_gpu/os_facts.rs`](../crates/rocm-core/src/host_gpu/os_facts.rs) has one reader per platform for the model and vendor, which `probe_cpu_linux` and `probe_cpu_windows` record and the summary reads). The first step of the subprocess runners is delivered too: `run_bounded` is the executor behind `run`, `capture_optional_command*` and the Windows diagnostic capture.
  - [`gfx_target.rs`](../crates/rocm-core/src/gfx_target.rs) is kept out of `host_gpu` so [`managed_runtime.rs`](../crates/rocm-core/src/managed_runtime.rs) reads the TheRock family mapping without importing the host probes.
  - Hardware probes resolve host paths through [`hardware_root.rs`](../crates/rocm-core/src/hardware_root.rs)'s `host_path`, which the E2E suite re-roots; [`os_release.rs`](../crates/rocm-core/src/os_release.rs) is the one `/etc/os-release` parser. `hardware_root.rs`'s `real_os_release` is the one reader of the real host's os-release for the callers that build a package-manager plan, and the resolver it passes is private; `read_os_release` itself is `pub` and takes any resolver, which [`examine/host_env.rs`](../crates/rocm-core/src/examine/host_env.rs) and [`host_gpu/os_facts.rs`](../crates/rocm-core/src/host_gpu/os_facts.rs) use with the simulated-root one. Nothing in `rocm-core` stops another caller doing the same; a test in [`system_packages.rs`](../apps/rocm/src/system_packages.rs) keeps `apps/rocm` from naming it.
- **Single sources.**
  - [`amd_smi.rs`](../crates/rocm-core/src/amd_smi.rs)'s `amd_smi_json` is the synchronous launch path for `amd-smi`, and the `/dev/kfd` pre-flight runs there; the dashboard collectors run their own pre-flight through the same bounded `rocm_core::device_readable_bounded` probe, over a `rocm-dash-collectors` to `rocm-core` edge that [`crate_edges.rs`](../xtask/src/crate_edges.rs) allows; [`amd_smi_launch_contract.rs`](../xtask/src/amd_smi_launch_contract.rs) fails any unlisted caller of `resolve_amd_smi_binary`.
  - [`log_tail.rs`](../crates/rocm-core/src/log_tail.rs) is the only log-tail reader behind every log view, and lives here because `rocmd` cannot depend on `rocm`.
  - A new atomic file write goes through [`atomic_write.rs`](../crates/rocm-core/src/atomic_write.rs); a few older temp-then-rename writers in `apps/rocm` predate it.
  - [`runtime.rs`](../crates/rocm-core/src/runtime.rs)'s `runtime_python_env_root_for_executable` and `install_root_has_payload` are the one definitions of those rules.
  - [`vllm_oom.rs`](../crates/rocm-core/src/vllm_oom.rs)'s `VLLM_OOM_DETECTED_PREFIX` and `VLLM_OOM_DIAGNOSE_COMMAND` must match byte for byte in the vLLM engine and `apps/rocm`.
- **Dependency direction.** [`automation.rs`](../crates/rocm-core/src/automation.rs) reads `WatcherMode` from [`config.rs`](../crates/rocm-core/src/config.rs), which imports nothing back; the built-in watcher catalog sits beside `WatcherMode` in [`config.rs`](../crates/rocm-core/src/config.rs) to keep it that way.
- **Reader threads.** [`process/bounded.rs`](../crates/rocm-core/src/process/bounded.rs)'s `run_with_timeout` and `run_bounded` abandon a pipe reader that has not finished within a 200 ms grace after the child is gone, so a grandchild holding a pipe cannot keep a call past its deadline by more than that grace. `run`, `run_with_env` and `run_raw` in [`probe_exec.rs`](../crates/rocm-core/src/probe_exec.rs), the optional capture in [`host_gpu/capture.rs`](../crates/rocm-core/src/host_gpu/capture.rs) and the Windows diagnostic capture in [`host_gpu/diagnostics.rs`](../crates/rocm-core/src/host_gpu/diagnostics.rs) all run on it. [`therock/process.rs`](../apps/rocm/src/therock/process.rs)'s `wait_with_output_bounded` is the one runner that still joins its reader threads with no time limit, so a grandchild holding a pipe can outlast its timeout.

- **vLLM throughput.** [`vllm_prom.rs`](../crates/rocm-dash-collectors/src/vllm_prom.rs) leaves `gen_tps` empty: the daemon runner turns the generation-token counter into a rate.
- **Engine label.** [`bench_load.rs`](../crates/rocm-dash-collectors/src/bench_load.rs) takes the `vllm` label from `EngineKind`, so the CSV `engine` column cannot drift from the registry's spelling. Because `engine` is a rollup key, a cell that mixes blank-engine and vLLM rows is reported through `EngineSplitNotice` for the CLI to print, not printed here.
- **Lemonade is off by default.** The daemon runs the Lemonade collector only when `RunnerOptions::enable_lemonade` is set; it defaults to false and the daemon `rocm dash` starts leaves it off.

- **A failed registry read retires nothing.** When a pass cannot read the registry in full, the runner retires no service; the records that did read still add and refresh their services, and the header warns until a read succeeds. - **No `rocm-core`.** The crate depends on `rocm-dash-core` and must not depend on `rocm-core` ([`crate_edges.rs`](../xtask/src/crate_edges.rs)).
  - `rocm-core` data reaches it through the [`tool_exec.rs`](../crates/rocm-dash-tui/src/tool_exec.rs) and [`registry_probe.rs`](../crates/rocm-dash-tui/src/registry_probe.rs) seams, which the `rocm` binary implements, or as values the binary plumbs in on `ResolvedArgs`.
  - A few values that mirror `rocm-core` (the default `rocm serve` port in [`llm.rs`](../crates/rocm-dash-tui/src/llm.rs), the runtime Python layout in [`ui/exec.rs`](../crates/rocm-dash-tui/src/ui/exec.rs)) are literal copies kept because of that rule; a change to the original needs the copy changed too.
  - `ManagedRegistryProbe` is read live, at each quit attempt and each frame the quit-confirm prompt is open, so an implementation must stay cheap (a local file read).
- **Windows.** There is no daemon socket on Windows: the `cfg(windows)` arm of [`client.rs`](../crates/rocm-dash-tui/src/client.rs) collects host and GPU metrics in-process through `rocm-dash-collectors`, the only use of that dependency, and the snapshot it posts does not replace the instance list.
- **Overlays and approvals.**
  - Each operational overlay is an `Option` state struct on `AppState` (`None` is closed); every opener calls `close_overlays` first, so at most one is open, and `draw_active_manager` draws it or its job console.
  - A mutating overlay action stages an `ApprovalRequest` in the overlay's own state; the job starts only on Approve and the `rocm` CLI does the mutation. Read-only actions start their job directly, and so does the bench-run form.
  - A chat tool call is approved separately, through `AppState::approval` and `tool_exec`'s `execute_approved`, which blocks and so runs off the async loop; the overlays do not use `tool_exec`.
- **Jobs.** One `State` holds every job (`AppState::jobs`), so closing an overlay leaves its jobs in the table. [`jobs.rs`](../crates/rocm-dash-tui/src/jobs.rs) sends events over an unbounded channel on purpose, because the synchronous reducer cannot apply backpressure, and the reducer bounds the output instead.
- **Reuse the shared components.**
  - A new screen reuses the approval prompt, job console, spinner, panel, theme tones, text-field edit and `ScrollState` that [`AGENTS.md`](../AGENTS.md) section 6 names, instead of hand-rolling its own.
  - [`dash_text_edit_contract.rs`](../xtask/src/dash_text_edit_contract.rs) fails a hand-rolled `push`/`pop` text edit outside [`ui/widgets.rs`](../crates/rocm-dash-tui/src/ui/widgets.rs); the Chat tab's input is the one exception.
- **Layering in `app/` and `ui/`.**
  - The modules split from [`app/event_loop.rs`](../crates/rocm-dash-tui/src/app/event_loop.rs) (`chat_runtime`, `focus`, `terminal`, `update_check`) are leaves: none calls back into it.
  - [`app/mod.rs`](../crates/rocm-dash-tui/src/app/mod.rs) re-exports the public surface its children took over, so `crate::app::` paths keep resolving.
  - The tabs only read `AppState` while drawing, except the Chat tab, which writes its measured scroll bounds back.
- **Single sources.**
  - `MENU_ITEMS` in [`app/types.rs`](../crates/rocm-dash-tui/src/app/types.rs) gives the Esc menu's rows, their labels, the key handling's wrap bound and the height `draw_menu` reserves.
  - `outlined_chip_spans` in [`ui/tabs/mod.rs`](../crates/rocm-dash-tui/src/ui/tabs/mod.rs) is the one tab geometry, behind both the painter and `compute_chip_layout`, which [`app/actions.rs`](../crates/rocm-dash-tui/src/app/actions.rs) uses to turn a click into a tab.
- **Endpoints and binds.**
  - [`llm.rs`](../crates/rocm-dash-tui/src/llm.rs) strips the API key and custom auth header from a loopback base URL, so a local endpoint is never sent a gateway credential.
  - [`ui/serve_wizard.rs`](../crates/rocm-dash-tui/src/ui/serve_wizard.rs) has its own stricter `is_loopback_host` (exact spellings only) for the bind host. Its default invocation is exactly `rocm serve MODEL`, so the CLI stays the authority for engine, GPU-required policy, host, port and managed mode.

Boundaries:

- The eight `*_contract.rs` files define no command: each is one `#[cfg(test)]` module run by `cargo test -p xtask`, and [`rust_source.rs`](../xtask/src/rust_source.rs) is declared test-only in [`main.rs`](../xtask/src/main.rs). The pull-request test selection narrows to the crates a change touches, so a change confined to another crate may not select them there; pushes to `main` and the merge queue run the whole workspace.
- [`affected.rs`](../xtask/src/affected.rs) is the one crate selection used by both CI's affected-crates job and [`prepush.rs`](../xtask/src/prepush.rs), which only widens it with `CROSS_CRATE_READS`; a change to how files are attributed to crates changes both.
- [`paths.rs`](../xtask/src/paths.rs) defines the workspace root, the active target directory and binary file names, honouring `CARGO_TARGET_DIR` and a cross-compilation target; a new task uses it rather than recomputing them.

Boundaries:

- **Test targets.** The `e2e` target behaves differently from the rest:
  - [`tests/e2e.rs`](../tests/e2e-cucumber/tests/e2e.rs) declares every `tests/e2e/` module in an inline `mod e2e`, and its target is `harness = false` and `test = false`, so the default test run skips it and `cargo xtask e2e` is how it normally runs.
  - A plain `#[test]` inside that target never runs: pure logic that needs unit tests goes in `src/`, or is included by a separate test target through `#[path]`, as [`tests/driver_host_guard.rs`](../tests/e2e-cucumber/tests/driver_host_guard.rs) includes [`tests/e2e/host_guard.rs`](../tests/e2e-cucumber/tests/e2e/host_guard.rs).
- The library target depends on no product crate. `rocm-core` is a dev-dependency only, used by unit tests and the `e2e` target, so library code repeats what it needs (as `device_memory::bounded_stdout` does) rather than add an edge `cargo xtask check-crate-edges` would flag.
- The report generator lives in [`crates/e2e-report`](../crates/e2e-report/src/lib.rs) so `xtask` can use it without this crate's dependency tree; [`src/lib.rs`](../tests/e2e-cucumber/src/lib.rs) re-exports it as `report`.
- **Copies of product logic that drift.** A product change here means a change in the suite:
  - [`src/capability.rs`](../tests/e2e-cucumber/src/capability.rs) re-implements the CLI's serve-engine choice and the AMD GPU count.
  - [`src/powershell_text_rule.rs`](../tests/e2e-cucumber/src/powershell_text_rule.rs) copies the rule in [`fix/catalog.rs`](../crates/rocm-core/src/fix/catalog.rs); both are tested against [`powershell_text_rule_cases.txt`](../tests/e2e-cucumber/fixtures/powershell_text_rule_cases.txt).
  - `cargo xtask demos` parses what [`src/bin/rocm-demo-env.rs`](../tests/e2e-cucumber/src/bin/rocm-demo-env.rs) prints.

## History

The crate roots (`apps/rocm`'s [`main.rs`](../apps/rocm/src/main.rs), `rocm-core`'s [`lib.rs`](../crates/rocm-core/src/lib.rs), `apps/rocmd`'s [`lib.rs`](../apps/rocmd/src/lib.rs) and others) once held most of their crate in one file and were split into the modules mapped above. Use `git log --follow <file>` for the history of a single module. This document describes only the current structure.
