# Architecture

This is the living module map for rocm-cli. It's a contributor-facing reference to where things live and why, updated in the same PR as the code it documents. It also tracks the files still pending modularization (see EAI-7768) so contributors know what's coming — but it is not a design-history document: entries describe current structure, not the decisions or debates that produced it.

> Before relying on any entry below, verify current file and function boundaries directly (e.g. `grep`) rather than trusting this doc's wording. Module boundaries shift as the codebase grows, and a stale-but-plausible-looking note is worse than an explicit prompt to check. Every concrete file citation in the Module map's per-crate inventories below — except "the old agent.rs" in the `rocm-dash-tui` entry (historical prose about a deleted file) and `report.json` in the `crates/e2e-report` entry (cucumber's untracked generated output) — is a relative markdown link rather than a bare filename, checked offline by [lychee](https://github.com/lycheeverse/lychee) in CI (the `docs-links` job, config in `lychee.toml`) — a moved or deleted file fails CI immediately, naming the broken link. That check doesn't check that the surrounding prose (e.g. which extraction pattern a module follows) is still accurate; the caution above still applies to everything but link resolution.

## Module organization convention

New subcommands and subsystems default to their own file from day one — they should not grow inside `main.rs`/`lib.rs` waiting for a future extraction pass. Two extraction patterns already exist in the codebase; use whichever fits:

- **Full domain extraction** — a subsystem's domain implementation moves into its own file that owns its own types (structs/enums), not just relocated functions; that ownership is usually what distinguishes this pattern from mechanical relocation below, though the Phase 6a variant described next shows ownership alone doesn't fully tell them apart — every `apps/rocm` module is a private `mod x;` regardless of pattern, so module privacy alone doesn't tell the two apart either. Full-domain-extraction modules are typically reached via qualified paths (e.g. `comfyui::render_status(...)`); mechanically relocated modules with no owned types are reached the same way (e.g. [`endpoint_keys.rs`](../apps/rocm/src/endpoint_keys.rs), [`logging.rs`](../apps/rocm/src/logging.rs)). The exception — reached unqualified through `use crate::x::{...}` re-imports, matching their dispatch call sites' pre-extraction form — is limited to the clusters that moved as a dispatch-adjacent group: [`automations.rs`](../apps/rocm/src/automations.rs), [`uninstall.rs`](../apps/rocm/src/uninstall.rs), and (as of Phase 6a, ROCMAI-82) [`driver_install.rs`](../apps/rocm/src/driver_install.rs), [`engines_cmd.rs`](../apps/rocm/src/engines_cmd.rs), [`serve_cmd.rs`](../apps/rocm/src/serve_cmd.rs). [`service_launch.rs`](../apps/rocm/src/service_launch.rs) (as of Phase 6b, ROCMAI-91) uses the same unqualified re-import form for its cross-module callers, but it is not a dispatch-adjacent cluster in the same sense — one of its callers, `automations.rs`, is not a dispatch call site, and its pre-extraction form was a qualified `crate::` call rather than an unqualified import, so the re-import is new rather than kept. This call-site form, not type ownership or dispatch-fn placement, is what actually separates the Phase 6a variant below from full domain extraction. Where a subsystem has a dedicated clap subcommand, its command *enum* usually stays in `main.rs` as part of the `Command`/`Cli` definition (e.g. `ComfyuiCommand`, `RuntimesCommand`) — but the dispatch function itself does not always stay with it: `comfyui()` does, while `engines()` (Phase 6a) and `runtimes()` (Phase 6c, ROCMAI-89) moved out to `engines_cmd.rs`/`runtimes_cmd.rs` respectively, following the mechanical-relocation re-import form below rather than full domain extraction's qualified-path form. Not every domain-extracted module has a dedicated command enum at all (`providers.rs` has none; it's invoked from the existing chat/config command flows). In library crates (`crates/rocm-core`) the module is `pub mod x;` plus a `pub use x::{...};` re-export, since it's part of the crate's public API. This is the default for new subsystems. Examples: [`apps/rocm/src/therock.rs`](../apps/rocm/src/therock.rs) (`RuntimesCommand`'s domain types), [`comfyui.rs`](../apps/rocm/src/comfyui.rs) (`ComfyuiCommand`), [`providers.rs`](../apps/rocm/src/providers.rs) (no dedicated command enum); `crates/rocm-core`'s [`diagnose.rs`](../crates/rocm-core/src/diagnose.rs)/[`examine.rs`](../crates/rocm-core/src/examine.rs).
- **Mechanical relocation** — a `pub(crate) fn` moves out verbatim, with shared types/config staying at the crate root and reached via `crate::`. Used for dispatch-adjacent clusters where a minimal, easy-to-review diff matters more than full extraction. Example: [`apps/rocm/src/automations.rs`](../apps/rocm/src/automations.rs). Variant: when the cluster is large enough to own private types (part of `main.rs`'s Phase 6a split, ROCMAI-82, `main.rs`'s Phase 6b split, ROCMAI-91, and `main.rs`'s Phase 6c split, ROCMAI-89), those types move with it instead of staying in `main.rs` — [`engines_cmd.rs`](../apps/rocm/src/engines_cmd.rs)'s types are used nowhere else, but [`driver_install.rs`](../apps/rocm/src/driver_install.rs)'s `DriverInstallResult`/`DriverInstallError` are `pub(crate)` and read from `main.rs`'s `install()` (`result.output`/`result.executed`, `error.source`/`error.executed`); [`serve_cmd.rs`](../apps/rocm/src/serve_cmd.rs)'s `ServeEngineSelection`/`ServeArgs` both stay `pub(crate)` and are both used from `main.rs` — `assess_model_for_host` calls `select_serve_engine` and reads the resulting `ServeEngineSelection`'s `.engine`/`.source` fields — and `ServeGenerationDefaults` is private; [`service_launch.rs`](../apps/rocm/src/service_launch.rs)'s `AttachOutcome`/`RawModeGuard`/`ManagedSpawn`/`AutostartClaim` are private, and its `ManagedLaunchReport` is `pub(crate)` and read from [`serve_cmd.rs`](../apps/rocm/src/serve_cmd.rs) for the interactive summary; [`runtimes_cmd.rs`](../apps/rocm/src/runtimes_cmd.rs)'s `RuntimeActivationResult` and `ActiveRuntimeMarker` are `pub(crate)` and read from `main.rs`'s `apply_runtime_update`/`append_update_activate_summary` and from [`storage.rs`](../apps/rocm/src/storage.rs) respectively; its sibling [`runtime_install_finalize.rs`](../apps/rocm/src/runtime_install_finalize.rs)'s `SdkInstallConsents` is `pub(crate)` and read from `main.rs`'s `install()`. The pattern is still "mechanical relocation" rather than full domain extraction because call sites keep their pre-extraction unqualified-re-import form — the exception named above — rather than switching to the qualified paths full-domain-extraction modules use. The top-level dispatch fns (`install()`/`dispatch()`) staying in `main.rs` is not what makes it so: full domain extraction usually keeps its dispatch fn in `main.rs` too (see `comfyui()` above).

There is no file-line-count CI gate enforcing this — `too_many_lines = "allow"` in the workspace `Cargo.toml` is a deliberate, function-level choice, not an oversight. This convention is the guardrail instead.

## Module map

Scoped to the crates that make up the shipped CLI/daemon/dashboard/engine surface, plus `crates/e2e-report` (a shared exception: it's HTML/markdown reporting consumed only by `xtask` and `tests/e2e-cucumber`, but it's still one of the modularization effort's target files, so it's mapped below). Dev-tooling and test-harness workspace members (`xtask`, `tests/e2e-cucumber` themselves) are otherwise out of scope — they're not part of the modularization effort's inventory.

Each per-crate module inventory lists one file per line. Flat inventories (every one below except `rocm-dash-tui`'s directory-split `agent/` and `app/` lists) are sorted alphabetically by filename, so a newly-extracted module has a predictable insertion point and doesn't force a rewrite of its neighbors; the `agent/` and `app/` lists instead keep `mod.rs` first, then the other files in logical (not alphabetical) order.

### `apps/rocm` — main CLI binary

[`main.rs`](../apps/rocm/src/main.rs) itself is **partially modularized** — Phase 6a (ROCMAI-82) extracted the driver-install/engines/serve clusters, Phase 6b (ROCMAI-91) extracted the managed-process-launch cluster, Phase 6c (ROCMAI-89) extracted the `runtimes` command/uninstall/rollback/SDK-install-finalization clusters, Phase 6d (ROCMAI-88) extracted the chat/assistant and MCP tool-bridge cluster below across three PRs; the rest of the split is planned across several more PRs, one cluster at a time (see EAI-7768).

- [`automations.rs`](../apps/rocm/src/automations.rs) — mechanical relocation, dispatch-adjacent, no owned types.
- [`bootstrap.rs`](../apps/rocm/src/bootstrap.rs) — a further-extracted variant of full domain extraction: it owns its clap command enum (`BootstrapCommand`) and dispatch function too, rather than leaving them in [`main.rs`](../apps/rocm/src/main.rs).
- [`chat.rs`](../apps/rocm/src/chat.rs) — full domain extraction (Phase 6d, ROCMAI-88), mirrors [`providers.rs`](../apps/rocm/src/providers.rs). Owns the chat/MCP-bridge cluster's types (`ChatRocmCommandAction`, `CommandCapture`, `DeterministicModelRecipe`, `DeterministicServiceRow`, `DeterministicEngineRow`, and others — all module-private except `ChatToolApprovalRequest`, reached by `dash_seam.rs` as `chat_tool_approval_request`'s return type), its validation/approval/execution logic (`validate_chat_tool_call` and the `validate_chat_*_tool_call` family), deterministic tool-output summarization (including `render_services_tool_result_text`), and the MCP tool-bridge entry points (`run_internal_mcp_call` and its helpers). [`main.rs`](../apps/rocm/src/main.rs), [`dash.rs`](../apps/rocm/src/dash.rs), and [`dash_seam.rs`](../apps/rocm/src/dash_seam.rs) call into it in production; [`comfyui.rs`](../apps/rocm/src/comfyui.rs) and [`runtime_install_finalize.rs`](../apps/rocm/src/runtime_install_finalize.rs) reference it only from their own `#[cfg(test)]` modules (`deterministic_comfyui_tool_summary` and `rocm_chat_tool_requested_args` respectively) — every one of these five files' references still goes through the `chat::` module boundary. As a child module of the crate root (`mod chat;` in `main.rs`), Rust's module-privacy rule already makes most of `main.rs`'s private helpers visible to `chat.rs` without any visibility change, when `chat.rs` calls into `main.rs`. The other direction needs real widening: `chat.rs`'s own functions reached from those five files — `run_internal_mcp_call` (a production call from `main.rs`), `rocm_chat_tool_requested_args` (reached only by `runtime_install_finalize.rs`'s own test module), among others — stay `pub(crate)`; the third PR's visibility audit tightened every other function to module-private, leaving 20 of `chat.rs`'s 123 functions `pub(crate)`, each with a confirmed external caller, production or test-only. The cluster's regression tests live in `chat.rs`'s own `mod tests`, moved out of `main.rs`'s shared `mod tests` block across the second and third PRs; two `main.rs` tests that reference `chat::` only incidentally — structural checks on `main.rs`'s own `dispatch()` source (`command_chat_honors_chat_mock_and_keeps_prompt_passthrough`, `command_chat_reads_prompt_from_piped_stdin`) — plus `serve_negative_sampling_space_form_reaches_range_validator`, a shared clap value-parser wiring test living alongside its sibling command-parsing tests, stay in `main.rs`.
- [`chat_host_facts.rs`](../apps/rocm/src/chat_host_facts.rs) — full domain extraction.
- [`cli_progress.rs`](../apps/rocm/src/cli_progress.rs) — shared CLI-output component (`Spinner`, `AnimatedSpinner`).
- [`cli_report.rs`](../apps/rocm/src/cli_report.rs) — shared CLI-output component (`ActionReport`).
- [`comfyui.rs`](../apps/rocm/src/comfyui.rs) — full domain extraction; serves the `comfyui` subcommand, whose command enum (`ComfyuiCommand`) and dispatch fn stay in [`main.rs`](../apps/rocm/src/main.rs) (unlike [`bootstrap.rs`](../apps/rocm/src/bootstrap.rs) above, which owns its own).
- [`dash.rs`](../apps/rocm/src/dash.rs) — full domain extraction.
- [`dash_seam.rs`](../apps/rocm/src/dash_seam.rs) — full domain extraction.
- [`driver_install.rs`](../apps/rocm/src/driver_install.rs) — mechanical relocation, owns private types (part of [`main.rs`](../apps/rocm/src/main.rs)'s Phase 6a split, ROCMAI-82; see the Phase 6a variant note above): `install_driver()`/`reconcile_driver_install()`, plus the driver-plan/state types.
- [`endpoint_keys.rs`](../apps/rocm/src/endpoint_keys.rs) — mechanical relocation, dispatch-adjacent, no owned types.
- [`engines_cmd.rs`](../apps/rocm/src/engines_cmd.rs) — mechanical relocation, owns private types (Phase 6a): `engines()`, plus env-root/runtime resolution — several helpers here are also called from [`serve_cmd.rs`](../apps/rocm/src/serve_cmd.rs) and from other root-level commands, so they stay `pub(crate)`.
- [`logging.rs`](../apps/rocm/src/logging.rs) — mechanical relocation, dispatch-adjacent, no owned types.
- [`provider_keys.rs`](../apps/rocm/src/provider_keys.rs) — full domain extraction.
- [`providers.rs`](../apps/rocm/src/providers.rs) — full domain extraction (no dedicated command enum; invoked from the existing chat/config command flows).
- [`runtime_install_finalize.rs`](../apps/rocm/src/runtime_install_finalize.rs) — mechanical relocation, owns private types (part of [`main.rs`](../apps/rocm/src/main.rs)'s Phase 6c split, ROCMAI-89, alongside [`runtimes_cmd.rs`](../apps/rocm/src/runtimes_cmd.rs) below): settling an engine onto a runtime after an SDK install — torch alignment, engine-dependency checks, and device checks. `SdkInstallConsents` is `pub(crate)` and read from `main.rs`'s `install()`; `ensure_openmpi_for_vllm`/`ensure_libatomic_for_torch`/`ensure_libnuma_for_torch`/`settle_engine_install` are also `pub(crate)` and read from [`engines_cmd.rs`](../apps/rocm/src/engines_cmd.rs).
- [`runtime_services.rs`](../apps/rocm/src/runtime_services.rs) — full domain extraction; reads the live local servers at activation time, classifies each against the runtime being activated, renders the report, and moves stale ones with `--restart-services`. `RuntimesCommand` and `fn runtimes()` moved to [`runtimes_cmd.rs`](../apps/rocm/src/runtimes_cmd.rs) in Phase 6c (ROCMAI-89); this file still owns `ServiceRuntimeState`/`RuntimeServiceEntry`/`FailedServiceRestart`/`RuntimeServiceReconciliation`/`ServiceRuntimePin`, reached from `runtimes_cmd.rs` via `crate::runtime_services`.
- [`runtimes_cmd.rs`](../apps/rocm/src/runtimes_cmd.rs) — mechanical relocation, owns private types (Phase 6c, ROCMAI-89): `runtimes()` and its activate/rollback/uninstall/import/adopt handlers, plus runtime manifest validation/registry. `RuntimesCommand` stayed in [`main.rs`](../apps/rocm/src/main.rs) (part of the `Command`/`Cli` clap definition, the same way `EnginesCommand` did in Phase 6a). `RuntimeActivationResult` and `ActiveRuntimeMarker` are `pub(crate)`, read from `main.rs`'s `apply_runtime_update`/`append_update_activate_summary` and from [`storage.rs`](../apps/rocm/src/storage.rs) respectively; `select_runtime_manifest`/`validate_runtime_manifest_for_activation`/`normalize_path_for_compare`/`recover_setup_runtime_registration`/`runtime_usability_status` are also `pub(crate)`, read from [`engines_cmd.rs`](../apps/rocm/src/engines_cmd.rs), [`storage.rs`](../apps/rocm/src/storage.rs), and [`comfyui.rs`](../apps/rocm/src/comfyui.rs). Calls into the sibling [`runtime_install_finalize.rs`](../apps/rocm/src/runtime_install_finalize.rs) above for the SDK-install-finalization bundle.
- [`serve_cmd.rs`](../apps/rocm/src/serve_cmd.rs) — mechanical relocation, owns private types (Phase 6a): `serve()`, plus engine-recipe overrides.
- [`serve_summary.rs`](../apps/rocm/src/serve_summary.rs) — full domain extraction.
- [`service_hints.rs`](../apps/rocm/src/service_hints.rs) — shared CLI-output component: the `rocm services stop|restart|remove <id> --yes` hint text, shared by [`main.rs`](../apps/rocm/src/main.rs), [`remote/mod.rs`](../apps/rocm/src/remote/mod.rs), [`serve_summary.rs`](../apps/rocm/src/serve_summary.rs), and [`service_launch.rs`](../apps/rocm/src/service_launch.rs) so they cannot go out of sync with each other, as `serve_summary.rs`'s stop row did from the day it was added — #417.
- [`service_launch.rs`](../apps/rocm/src/service_launch.rs) — mechanical relocation, owns private types (Phase 6b, ROCMAI-91): spawning/attaching to a managed service process and streaming its log, plus the endpoint-key/auth checks that gate a public bind — `AttachOutcome`/`RawModeGuard`/`ManagedSpawn`/`AutostartClaim` are its private types; `ManagedLaunchReport` is `pub(crate)`, since [`serve_cmd.rs`](../apps/rocm/src/serve_cmd.rs) reads its fields directly for the interactive summary. Most of this module's functions are `pub(crate)` for the same reason — [`main.rs`](../apps/rocm/src/main.rs), [`serve_cmd.rs`](../apps/rocm/src/serve_cmd.rs), and [`automations.rs`](../apps/rocm/src/automations.rs) all call into it. `ServicesCommand`/`services()` stayed in [`main.rs`](../apps/rocm/src/main.rs) rather than moving alongside — the service-record-management helpers `services()` dispatches to (stop/restart/remove/prune) are entangled with each other; only stop/restart are also reachable from the chat/LLM sandbox tool-calling path, out of scope for Phase 6b.
- [`storage.rs`](../apps/rocm/src/storage.rs) — full domain extraction.
- [`therock.rs`](../apps/rocm/src/therock.rs) — full domain extraction; owns TheRock SDK install/update and the runtime-manifest model/loaders. The `runtimes` subcommand's own command enum, dispatch fn, and most of its domain logic — rendering, activation, and manifest import — stay in [`main.rs`](../apps/rocm/src/main.rs).
- [`uninstall.rs`](../apps/rocm/src/uninstall.rs) — mechanical relocation, owns private types: `uninstall()`, plus the installer `PATH` undo and running-executable deletion. The shared plan type and its file-removal helpers stay in [`main.rs`](../apps/rocm/src/main.rs) because [`storage.rs`](../apps/rocm/src/storage.rs) reuses them.

### `apps/rocmd` — background daemon

Modularized (ROCMAI-83, Phase 5 of EAI-7768's sequencing):

- [`cli.rs`](../apps/rocmd/src/cli.rs) — the `Cli`/`Command` clap definitions, `SandboxToolArg`/`SandboxToolPolicy`, the bridge-snapshot diagnostic printer, and the top-level dispatch in `run_cli`/`run_bin_cli`/`run_from_args`.
- [`common.rs`](../apps/rocmd/src/common.rs) — helpers shared across ≥2 of the other clusters: GPU/amd-smi snapshotting, the bridge-snapshot diagnostic, `CommandCapture` and the shared `rocm`-subprocess capture helpers the sandbox and MCP clusters both call (the bounded-execution half of that plumbing lives in [`process.rs`](../crates/rocm-core/src/process.rs) rather than here), and small arg/healthcheck/endpoint-key utilities. A helper earns a place here only once a second still-inline cluster calls it directly; a helper with exactly one caller stays next to that caller until its own cluster's extraction PR, even if it is conceptually similar to something that did move.
- [`mcp.rs`](../apps/rocmd/src/mcp.rs) — the MCP stdio server, tool schema table, tool dispatch, and the `rocm`-subprocess capture/argv-building helpers behind the MCP tools.
- [`persistence.rs`](../apps/rocmd/src/persistence.rs) — `record_event`/`load_managed_services`, the automation-event/audit-log and managed-service-registry I/O shared across the daemon's sandbox, MCP, service-lifecycle, and watcher code.
- [`sandbox.rs`](../apps/rocmd/src/sandbox.rs) — bubblewrap/native sandbox execution, atomic-write helpers, artifact prefetch policy gating, and the sandbox-tool result shaping for `check_updates`/`driver_plan`.
- [`service.rs`](../apps/rocmd/src/service.rs) — managed-service PID lifecycle/stop, `run_daemon`'s foreground loop, `supervise_service`'s spawn-and-recover path, and serve-log startup-phase polling.
- [`watchers.rs`](../apps/rocmd/src/watchers.rs) — event collection/dispatch for all built-in watchers (TheRock update, GPU metrics/thermal-pressure, cache-warm, driver-upgrade, server-recover), plus managed-service recovery classification and automation-proposal queuing.
- [`webhook.rs`](../apps/rocmd/src/webhook.rs) — the local webhook source: its axum routes, request validation, and watcher-kind allow-list.

[`lib.rs`](../apps/rocmd/src/lib.rs) itself is now top-level glue: module declarations and the two externally-consumed entry points (`run_bin_cli`/`run_from_args`, re-exported from [`cli.rs`](../apps/rocmd/src/cli.rs)).

### `crates/rocm-core` — core library

Already-extracted subsystem modules, following the same full-domain-extraction pattern (and several further siblings beyond these):

- [`automation.rs`](../crates/rocm-core/src/automation.rs) — (ROCMAI-151, Phase 7d) the built-in automation-watcher catalog, automation-daemon runtime state, and its on-disk event/proposal/audit records — see the module's own doc comment for what it owns. [`config.rs`](../crates/rocm-core/src/config.rs) and this module depend on each other — `config.rs` imports `BuiltinWatcherSpec` from here, and this module imports `WatcherMode` from `config.rs` — a back-edge the split introduces without eliminating; `WatcherMode` stays with the persisted config because it is part of `RocmCliConfig`'s own on-disk shape, not an automation-daemon concern.
- [`binary_paths.rs`](../crates/rocm-core/src/binary_paths.rs) — (ROCMAI-151, Phase 7d) locating `rocm-engine-<name>` siblings, and the CLI binary itself (a sibling `rocm` only when running from a cargo `deps/` directory).
- [`config.rs`](../crates/rocm-core/src/config.rs) — (ROCMAI-151, Phase 7d) the unified `RocmCliConfig` and its nested sections, including the persisted `WatcherMode` enum (the built-in watcher catalog itself lives in [`automation.rs`](../crates/rocm-core/src/automation.rs)) and the rocm-dash dashboard sub-config — see the module's own doc comment for what it owns.
- [`crypto.rs`](../crates/rocm-core/src/crypto.rs) — (ROCMAI-152, Phase 7c) RSASSA-PKCS#1 v1.5/SHA-256 sign/verify, generic — not model-catalog-specific.
- [`diagnose.rs`](../crates/rocm-core/src/diagnose.rs)
- [`examine.rs`](../crates/rocm-core/src/examine.rs)
- [`host_gpu.rs`](../crates/rocm-core/src/host_gpu.rs) — (ROCMAI-85, Phase 7a of EAI-7768's sequencing) GPU/host hardware detection — see the module's own doc comment for what it owns.
- [`managed_runtime.rs`](../crates/rocm-core/src/managed_runtime.rs) — (ROCMAI-85, Phase 7a) the TheRock managed-runtime-environment surface — see the module's own doc comment for what it owns.
- [`model_catalog.rs`](../crates/rocm-core/src/model_catalog.rs) — (ROCMAI-152, Phase 7c) the curated model catalog's types, built-in catalog JSON loading, signed external recipe indexes, and artifact cache-marker bookkeeping — see the module's own doc comment for what it owns.
- [`model_readiness.rs`](../crates/rocm-core/src/model_readiness.rs) — the `rocm diagnose --model`/`rocm model --verbose` fit assessment: curated-recipe lookup against a host's measured GPU/RAM, shared between the two commands so they cannot disagree about whether a model fits.
- [`net.rs`](../crates/rocm-core/src/net.rs) — (ROCMAI-154, Phase 7b) networking/download/endpoint-readiness primitives.
- [`paths.rs`](../crates/rocm-core/src/paths.rs) — (ROCMAI-154, Phase 7b) `AppPaths` and its filesystem-location primitives.
- [`process.rs`](../crates/rocm-core/src/process.rs) — (ROCMAI-154, Phase 7b) process-spawn/terminate primitives, including `FileLock`, plus `run_with_timeout`: it drains both pipes on their own threads from the moment the child starts, so output size cannot stall a command into its own timeout, and it bounds how much of a timed-out child's output the error quotes, because that text reaches persisted automation logs. It is not yet the *only* such helper — [`therock.rs`](../apps/rocm/src/therock.rs)'s `wait_with_output_bounded`, [`examine.rs`](../crates/rocm-core/src/examine.rs)'s `run_raw`, and [`host_gpu.rs`](../crates/rocm-core/src/host_gpu.rs)'s `capture_optional_command_candidate_with_timeout` (plus its Windows-only `capture_diagnostic_command`) still join their reader threads with no time limit, so a grandchild holding the pipe can outlast their timeout; converging them onto `run_with_timeout` is follow-up work to ROCMAI-448 tracked in [#623](https://github.com/ROCm/rocm-cli/issues/623).
- [`rocm_install.rs`](../crates/rocm-core/src/rocm_install.rs) — (ROCMAI-85, Phase 7a) unmanaged ("legacy") ROCm install discovery — see the module's own doc comment for what it owns.
- [`service_record.rs`](../crates/rocm-core/src/service_record.rs) — (ROCMAI-151, Phase 7d) `ManagedServiceRecord`, the on-disk manifest for a managed inference service — see the module's own doc comment for what it owns.

Still in [`lib.rs`](../crates/rocm-core/src/lib.rs), none of it claimed by any phase-7 cluster (see ROCMAI-200 for each): amd-smi binary resolution (`resolve_amd_smi_binary*`), which consumes [`managed_runtime.rs`](../crates/rocm-core/src/managed_runtime.rs)'s registry records but is a distinct, not-yet-scoped concern; the generic cross-cutting helpers `torch_alignment_disabled`/`require_nonempty`/`command_failure_detail`/`write_atomic` (the last shared by [`config.rs`](../crates/rocm-core/src/config.rs), [`automation.rs`](../crates/rocm-core/src/automation.rs), and [`service_record.rs`](../crates/rocm-core/src/service_record.rs) for their own atomic-replace writes); `VLLM_GPU_MEMORY_UTILIZATION_HINT`, embedded in the middle of the amd-smi resolution family despite being unrelated to it; the generated endpoint-API-key helpers (`generate_endpoint_api_key`/`endpoint_api_key_has_forbidden_chars`), unrelated to crypto or model-catalog despite sitting in the same stretch of the file pre-split; the `CodexBridgeSnapshot`/`CodexBridgeGpuSnapshot`/`CodexBridgeEngine` bridge DTOs, deliberately excluded from [`binary_paths.rs`](../crates/rocm-core/src/binary_paths.rs) by that phase's own scope but not claimed by anything else either; and `ServiceId`/`generate_service_id`/`sanitize_component`/`unix_time_millis`, not part of either [`service_record.rs`](../crates/rocm-core/src/service_record.rs) or [`binary_paths.rs`](../crates/rocm-core/src/binary_paths.rs) (`unix_time_millis` in particular is a crate-wide generic time helper used by several of this crate's own sibling modules, not service-record-specific).

[`lib.rs`](../crates/rocm-core/src/lib.rs) itself is **not yet fully modularized** — see EAI-7768, planned last in the modularization effort: highest fan-in (every app and engine crate depends on it), but lowest novelty since the existing sibling modules already prove the pattern works.

### `crates/e2e-report`

Modularized (EAI-8032, Phase 1 of EAI-7768's sequencing):

- [`command_coverage.rs`](../crates/e2e-report/src/command_coverage.rs) — (ROCMAI-486, Phase 1 of a staged further split of [`consolidated.rs`](../crates/e2e-report/src/consolidated.rs)) the CLI command-coverage audit table — which `rocm` commands were exercised and whether they passed — consumes `consolidated::PlatformReport` but shares no type with the `Grid`/reconciliation model itself.
- [`components.rs`](../crates/e2e-report/src/components.rs) — shared maud HTML fragment rendering, plus the CSS and timestamp helpers both generators use, depending only on [`parse.rs`](../crates/e2e-report/src/parse.rs) types to keep the module graph acyclic.
- [`consolidated.rs`](../crates/e2e-report/src/consolidated.rs) — the `PlatformReport`/manifest/expectation model and the reconciled scenario × platform `Grid`, plus the multi-platform HTML/markdown generation built on top — still the largest module, still bundling manifest/command parsing, the `Grid`/`PlatformReport` model, and both HTML and markdown rendering in one file; remaining clusters are tracked on ROCMAI-486.
- [`parse.rs`](../crates/e2e-report/src/parse.rs) — cucumber `report.json` data model, parsing, and `@expected-failure` xfail evaluation.
- [`single_report.rs`](../crates/e2e-report/src/single_report.rs) — single-platform HTML report generation.

These modules are private `mod` declarations — [`lib.rs`](../crates/e2e-report/src/lib.rs) re-exports only the selected public API surface (`XfailReport`, `evaluate_xfail`, `scenario_results_by_id`, `generate`, `RunMeta`, `PlatformReports`, `load_platform_reports`, `generate_consolidated`, `consolidated_summary_markdown`) via `pub use`, so consumers reach it through the crate root rather than through module-qualified paths like `e2e_report::parse::...`. `generate_consolidated` and `consolidated_summary_markdown` take the opaque `PlatformReports` bundle [`load_platform_reports`](../crates/e2e-report/src/consolidated.rs) returns (ROCMAI-484 / ROCm/rocm-cli#640) — bundling the parsed reports with the `inputs` they came from means a caller producing both outputs can no longer pass the two out of sync with each other, and `PlatformReport` itself went back to `pub(crate)` once the bundle was the only thing outside callers needed. This is a deliberate encapsulation choice tighter than the full-domain-extraction convention's `pub mod x;` + `pub use x::{...};` default described above — nothing outside this crate needs the module paths themselves, only the re-exported items. Unlike [`components.rs`](../crates/e2e-report/src/components.rs), which, as noted above, keeps the module graph acyclic by depending only on [`parse.rs`](../crates/e2e-report/src/parse.rs), [`command_coverage.rs`](../crates/e2e-report/src/command_coverage.rs) and [`consolidated.rs`](../crates/e2e-report/src/consolidated.rs) depend on each other — [`consolidated.rs`](../crates/e2e-report/src/consolidated.rs) calls `command_coverage::command_coverage_markdown`, and [`command_coverage.rs`](../crates/e2e-report/src/command_coverage.rs) consumes `consolidated::PlatformReport` (via its `commands`, `label` and `scenario_pass_map()`) — a back-edge the split introduces without eliminating.

### `engines/lemonade`, `engines/vllm` — inference engine adapters

`engines/vllm` follows full domain extraction:

- [`install.rs`](../engines/vllm/src/install.rs) — ROCm/vLLM build-variant discovery, install execution, and runtime-repair assessment.
- [`process.rs`](../engines/vllm/src/process.rs) — spawn/env/path setup and readiness polling.
- [`runtime.rs`](../engines/vllm/src/runtime.rs) — TheRock/managed-runtime resolution and TheRock library/bin path derivation; derives paths only, performing no filesystem writes itself. The launch path's compat-shim writes (a `libmpi_cxx` stub, stale-numa-shim removal) live in the separate `ensure_therock_compat_shims`, called from `process.rs`; the running-state payload, which never calls it, falls back to a plain directory listing instead.
- [`state.rs`](../engines/vllm/src/state.rs) — service state file I/O, log tailing, and health/inference probing.

[`lib.rs`](../engines/vllm/src/lib.rs) keeps only CLI/envelope dispatch and the few items shared across those modules.

`engines/lemonade` follows the same pattern:

- [`backend_alignment.rs`](../engines/lemonade/src/backend_alignment.rs) — ROCm-SDK-to-llama.cpp-backend Tier 1/Tier 2/revert alignment and backend discovery/install/selection.
- [`direct_llama.rs`](../engines/lemonade/src/direct_llama.rs) — Hugging Face checkpoint/GGUF resolution and the direct-llama-server serve path.
- [`install.rs`](../engines/lemonade/src/install.rs) — embeddable-runtime archive download/verify/extract, cache locking, and manifest persistence.
- [`process.rs`](../engines/lemonade/src/process.rs) — `lemond`/llama-server spawn, env/path setup, and readiness/health polling.
- [`runtime_dir.rs`](../engines/lemonade/src/runtime_dir.rs) — `XDG_RUNTIME_DIR` tier1/2/3 hardening for the spawned child.
- [`state.rs`](../engines/lemonade/src/state.rs) — service state file I/O, device-policy/GPU-selection parsing, and port/endpoint helpers.

[`lib.rs`](../engines/lemonade/src/lib.rs) keeps only CLI/envelope dispatch and the service-lifecycle orchestration that calls across those modules.
