# Architecture

This is the living module map for rocm-cli. It's a contributor-facing reference to where things live and why, updated in the same PR as the code it documents. It documents what exists now; the few moves that are still deferred are called out in the entries they affect. Phase labels such as "Phase 5 of ROCMAI-27's sequencing" name the original modularization effort's ordering and are kept only so a module can be traced to the ticket that moved it. It is also not a design-history document: entries describe current structure, not the decisions or debates that produced it.

> Before relying on any entry below, verify current file and function boundaries directly (e.g. `grep`) rather than trusting this doc's wording. Module boundaries shift as the codebase grows, and a stale-but-plausible-looking note is worse than an explicit prompt to check. Every concrete file citation in the Module map's per-crate inventories below — except "the old agent.rs" in the `rocm-dash-tui` entry (historical prose about a deleted file) and `report.json` in the `crates/e2e-report` entry (cucumber's untracked generated output) — is a relative markdown link rather than a bare filename, checked offline by [lychee](https://github.com/lycheeverse/lychee) in CI (the `docs-links` job, config in `lychee.toml`) — a moved or deleted file fails CI immediately, naming the broken link. That check doesn't check that the surrounding prose (e.g. which extraction pattern a module follows) is still accurate; the caution above still applies to everything but link resolution.

A second check runs the other way: `cargo xtask check-architecture-doc` ([`architecture_doc.rs`](../xtask/src/architecture_doc.rs)) fails when a production source file — a `.rs` file under `apps/*/src`, `crates/*/src` or `engines/*/src` — has no link in this document, so a new module cannot land without an entry. Only a link that renders as one counts: a path inside an HTML comment, a code block or a code span does not, and neither does a malformed link (one missing its `[` or `)`, or with an escaped bracket), an image, or the outer brackets of a link that contains another link. Write the entry as an inline `[text](path)` link with its text on one line; `<path>` delimiters around the destination are accepted, but reference-style links, a `?query` suffix and root-relative paths are not. `build.rs` files and the `tests/` and `examples/` trees are out of scope. It runs in the `clippy` CI job and in the `architecture-doc` prek hook, at commit and at push. Test-only helpers (`test_support.rs`, `test_env.rs`, `*_proptests.rs`, `*_props.rs`, `*_properties.rs`) need no entry. Every production file has an entry, so the check's `EXEMPT` list is empty and capped at zero; adding a file to it to make the check pass is not the way, and growing it is a visible, reviewed exception.

## Module organization convention

New subcommands and subsystems default to their own file from day one — they should not grow inside `main.rs`/`lib.rs` waiting for a future extraction pass. Two extraction patterns already exist in the codebase; use whichever fits:

- **Full domain extraction** — a subsystem's domain implementation moves into its own file that owns its own types (structs/enums), not just relocated functions; that ownership is usually what distinguishes this pattern from mechanical relocation below, though the Phase 6a variant described next shows ownership alone doesn't fully tell them apart — every `apps/rocm` module is a private `mod x;` regardless of pattern, so module privacy alone doesn't tell the two apart either. Full-domain-extraction modules are typically reached via qualified paths (e.g. `comfyui::render_status(...)`); mechanically relocated modules with no owned types are reached the same way (e.g. [`endpoint_keys.rs`](../apps/rocm/src/endpoint_keys.rs), [`logging.rs`](../apps/rocm/src/logging.rs)). The exception — reached unqualified through `use crate::x::{...}` re-imports, matching their dispatch call sites' pre-extraction form — is limited to the clusters that moved as a dispatch-adjacent group; the block of `use crate::x::{...}` re-imports near the top of [`main.rs`](../apps/rocm/src/main.rs) is the current list of the modules it reaches that way (a few of them re-imported for reasons other than dispatch, as the comment above the block explains). [`service_launch.rs`](../apps/rocm/src/service_launch.rs) (as of Phase 6b, ROCMAI-91) uses the same unqualified re-import form for its cross-module callers, but it is not a dispatch-adjacent cluster in the same sense — one of its callers, `automations.rs`, is not a dispatch call site, and its pre-extraction form was a qualified `crate::` call rather than an unqualified import, so the re-import is new rather than kept. This call-site form, not type ownership or dispatch-fn placement, is what actually separates the Phase 6a variant below from full domain extraction. Where a subsystem has a dedicated clap subcommand, its command *enum* usually lives in [`cli.rs`](../apps/rocm/src/cli.rs) as part of the `Command`/`Cli` definition (e.g. `ComfyuiCommand`, `RuntimesCommand`), the way [`apps/rocmd`](../apps/rocmd/src/cli.rs) keeps its command tree in a `cli.rs` of its own — but the dispatch function, the match over that tree, does not stay in `main.rs` with it: `comfyui::run` lives in `comfyui.rs`, reached by the qualified path full domain extraction uses, while `engines()` and `runtimes()` moved out to `engines_cmd.rs`/`runtimes_cmd.rs` respectively, following the mechanical-relocation re-import form below. Only the top-level `dispatch()`, the match that sends each `Command` variant to its handler, stays in `main.rs`. Not every domain-extracted module has a dedicated command enum at all (`providers.rs` has none; it's invoked from the existing chat/config command flows). In library crates (`crates/rocm-core`) the module is `pub mod x;` plus a `pub use x::{...};` re-export, since it's part of the crate's public API. This is the default for new subsystems. Examples: [`apps/rocm/src/therock.rs`](../apps/rocm/src/therock.rs) (TheRock SDK install orchestration, with its update planning and other clusters in `therock/` child modules and no command enum of its own), [`comfyui.rs`](../apps/rocm/src/comfyui.rs) (`ComfyuiCommand`), [`providers.rs`](../apps/rocm/src/providers.rs) (no dedicated command enum); `crates/rocm-core`'s [`diagnose.rs`](../crates/rocm-core/src/diagnose.rs)/[`examine.rs`](../crates/rocm-core/src/examine.rs).
- **Mechanical relocation** — a `pub(crate) fn` moves out verbatim, with shared types/config staying at the crate root and reached via `crate::`. Used for dispatch-adjacent clusters where a minimal, easy-to-review diff matters more than full extraction. Example: [`apps/rocm/src/update_cmd.rs`](../apps/rocm/src/update_cmd.rs). Variant: when the cluster is large enough to own types (part of `main.rs`'s Phase 6a split, ROCMAI-82, `main.rs`'s Phase 6b split, ROCMAI-91, `main.rs`'s Phase 6c split, ROCMAI-89, and Phase 6e's follow-up, ROCMAI-726), those types move with it instead of staying in `main.rs` — [`engines_cmd.rs`](../apps/rocm/src/engines_cmd.rs)'s types are used nowhere else, but [`driver_install.rs`](../apps/rocm/src/driver_install.rs)'s `DriverInstallResult`/`DriverInstallError` are `pub(crate)` and read from [`install_cmd.rs`](../apps/rocm/src/install_cmd.rs)'s `install()` (`result.output`/`result.executed`, `error.source`/`error.executed`); [`freeform_execution.rs`](../apps/rocm/src/freeform_execution.rs)'s `FreeformExecution` is `pub(crate)` and read from `main.rs`'s `execute_freeform_next_action()` (`execution.action`) — it was already `pub(crate)` before the split, unlike the two functions that return/consume it, which widened from module-private; [`serve_cmd.rs`](../apps/rocm/src/serve_cmd.rs)'s `ServeEngineSelection`/`ServeArgs` both stay `pub(crate)` and are used from `main.rs` (`ServeArgs`) and [`model_fit.rs`](../apps/rocm/src/model_fit.rs) (`assess_model_for_host` calls `select_serve_engine` and reads the resulting `ServeEngineSelection`'s `.engine`/`.source` fields) — and `ServeGenerationDefaults` moved out with the engine-recipe overrides to [`serve_recipe.rs`](../apps/rocm/src/serve_recipe.rs), where it and its fields are `pub(crate)` because `serve()` builds it; [`service_launch.rs`](../apps/rocm/src/service_launch.rs)'s `AttachOutcome`/`RawModeGuard`/`ManagedSpawn`/`AutostartClaim` are private, and its `ManagedLaunchReport` is `pub(crate)` and read from [`serve_cmd.rs`](../apps/rocm/src/serve_cmd.rs) for the interactive summary; [`runtimes_cmd.rs`](../apps/rocm/src/runtimes_cmd.rs)'s `RuntimeActivationResult` and `ActiveRuntimeMarker` are `pub(crate)` and read from [`update_cmd.rs`](../apps/rocm/src/update_cmd.rs)'s `apply_runtime_update`/`append_update_activate_summary` and from [`storage.rs`](../apps/rocm/src/storage.rs) respectively; its sibling [`runtime_install_finalize.rs`](../apps/rocm/src/runtime_install_finalize.rs)'s `SdkInstallConsents` is `pub(crate)` and read from `install_cmd.rs`'s `install()`. The pattern is still "mechanical relocation" rather than full domain extraction because call sites keep their pre-extraction unqualified-re-import form — the exception named above — rather than switching to the qualified paths full-domain-extraction modules use. Where a subcommand's dispatch fn lives is not what makes it so: a full-domain-extraction module can host its own dispatch fn too (see `comfyui::run` above).

Moving a `proptest!` block to another file leaves its saved failure cases behind unless they are carried over: proptest keys them by the test's source file (`<crate>/src/<path>.rs` reads `<crate>/proptest-regressions/<path>.txt`, where `src/` is the directory holding `main.rs` or `lib.rs`) and does not warn when the file stops matching. Carry them in the same commit, and how depends on how much moved. When every property test of the file moves and the new file has no regression file yet, `git mv` the old one to the name the new file needs. When only some move, the tests left behind still read the old file, so keep it, and copy the saved cases to the new file's regression file (appending to it when it already exists, so its own cases stay). An `xtask` test fails the build on a regression file no test reads; it cannot notice a regression file that was moved away from tests that still need it, so check a split's diff for that. See [Property tests](testing.md#property-tests).

A flat size limit backs this convention: `cargo xtask check-module-size` ([`module_size.rs`](../xtask/src/module_size.rs)) reports every source file with more than 1,500 production lines, and there is one limit for every file, with no per-file ceilings, baseline or exemption. Production lines exclude test-gated items (inline `#[cfg(test)]` modules and the like), and test-only files are not source files; the exact definition is at the top of that file. Today the check is advisory: the `clippy` CI job and the `cargo-module-size` pre-commit hook print the offenders without failing, until the files over the limit have been split. A PR that would push a file past 1,500 production lines splits it in the same change (a pure move, the tests moving with the code, this document updated in the same PR); raising the limit or exempting a file is not an option for a feature PR. A change that merely edits a file that is already over the limit does not by itself have to split it: those files are split under their own tickets, and the check becomes blocking only once none is left. `too_many_lines = "allow"` in the workspace `Cargo.toml` stays a deliberate function-level choice; this gate is about files.

## Module map

Scoped to the crates that make up the shipped CLI/daemon/dashboard/engine surface, plus `crates/e2e-report` (a shared exception: it's HTML/markdown reporting consumed only by `xtask` and `tests/e2e-cucumber`, but it's still one of the modularization effort's target files, so it's mapped below). Dev-tooling and test-harness workspace members (`xtask`, `tests/e2e-cucumber` themselves) are otherwise out of scope — they're not part of the modularization effort's inventory.

Each per-crate module inventory lists one file per line. Flat inventories (every one below except `rocm-dash-tui`'s directory-split `agent/`, `app/` and `ui/tabs/` lists, `e2e-report`'s directory-split `consolidated/` list and the `engines/aim` list) are sorted alphabetically by filename, so a newly-extracted module has a predictable insertion point and doesn't force a rewrite of its neighbors; the `agent/`, `app/` and `consolidated/` lists instead keep `mod.rs` first, then the other files in logical (not alphabetical) order, and the `ui/tabs/` list keeps `mod.rs` first and then sorts the tabs alphabetically.

### `apps/rocm` — main CLI binary

[`main.rs`](../apps/rocm/src/main.rs) is the crate root. Besides smaller helpers, it holds `main()`, `run()` and `dispatch()`, the match over the clap `Cli`/`Command` tree that [`cli.rs`](../apps/rocm/src/cli.rs) defines; the builders that turn that tree into a `clap::Command` (`cli_command()`, `completion_command()`); the command handlers still defined here (`version()` and `launch_default()`, the no-subcommand arm); freeform-invocation routing (`parse_freeform_invocation`, `should_treat_as_freeform`, `run_freeform`, `execute_freeform_next_action`, `treat_as_natural_language`); a few crate-root items several modules share (`status_for_readiness`, `device_policy_name`, `engine_inventory`, `ROLLBACK_RECOVERY_HINT`); the `use crate::x::{...}` re-import block described above, which also re-imports the `cli.rs` types so other modules keep reaching them as `crate::Command`, `crate::Provider` and so on; and the crate's shared `mod tests` block.

- [`automations.rs`](../apps/rocm/src/automations.rs) — mechanical relocation, owns private types (Phase 6f, ROCMAI-210): the `rocm automations` dispatch handler (`automations()`) plus the `rocm automations` status report it prints (`render_automations_text`), the `ProposalKind` classification that report renders through (`proposal_kind`, `fallback_tool_for_automation_action`, `proposal_plain_summary`, `proposal_plain_reason`), the small plain-language label helpers (`proposal_status_label`, `proposal_bool_argument`, `automation_event_plain_summary`, `audit_event_plain_summary`, `watcher_mode_plain_label`, `watcher_last_check`, `watcher_plain_name`, `watcher_plain_trigger`, `watcher_plain_action`, `watcher_policy_note`), and the unrelated `rocm daemon --status` summary (`render_daemon_text`). `render_automations_text` and `render_daemon_text` are `pub(crate)`: [`main.rs`](../apps/rocm/src/main.rs)'s `dispatch()` calls `render_daemon_text` directly (re-imported alongside `automations` via `use crate::automations::{automations, render_daemon_text};`; `render_automations_text` has no `dispatch()` call site of its own, reached only through `automations()` above, now local to this file), and [`chat/mcp_bridge.rs`](../apps/rocm/src/chat/mcp_bridge.rs)'s read-only command runner calls both. Every other item in this list, including `watcher_policy_note` (called from `automations()`'s `Enable` arm and from `render_automations_text`, both in this same file), has no caller outside this module and stays private. The cluster's regression tests live in this module's own `mod tests`, reaching the shared `test_paths` fixture through `crate::tests::` the same way other mechanically relocated modules do.
- [`background_helper.rs`](../apps/rocm/src/background_helper.rs) — mechanical relocation out of [`service_launch.rs`](../apps/rocm/src/service_launch.rs), owns one `pub(crate)` type: what the CLI can tell about the background automation helper (`rocm daemon`). It holds `background_helper_already_running` (the file-based liveness check behind the no-double-spawn decision), the `HelperNote` type and `background_helper_note` with its `helper_note_for` wording, which [`services_text.rs`](../apps/rocm/src/services_text.rs) prints after a stop and [`uninstall_plan.rs`](../apps/rocm/src/uninstall_plan.rs) turns into an uninstall warning. Spawning the helper (`ensure_background_helper_running` and its autostart lock) stays in [`service_launch.rs`](../apps/rocm/src/service_launch.rs), which reads `background_helper_already_running` from here. The module is a leaf: it imports nothing from the service modules, so the note can be read from [`services_text.rs`](../apps/rocm/src/services_text.rs) without that module importing the one that spawns services. The cluster's regression tests live in this module's own `mod tests`, which stays private: the `runtime_state` and `set_helper_facts` fixtures they share with the helper-autostart and stop-output tests in [`service_launch.rs`](../apps/rocm/src/service_launch.rs) live in the crate-level [`test_support.rs`](../apps/rocm/src/test_support.rs).
- [`bootstrap.rs`](../apps/rocm/src/bootstrap.rs) — a further-extracted variant of full domain extraction: it owns its clap command enum (`BootstrapCommand`) and dispatch function too, rather than leaving the enum in [`cli.rs`](../apps/rocm/src/cli.rs) and the dispatch in [`main.rs`](../apps/rocm/src/main.rs).
- [`bridge_snapshot.rs`](../apps/rocm/src/bridge_snapshot.rs) — mechanical relocation, no owned types: the host snapshot behind the internal bridge surface (`build_codex_bridge_snapshot`, `build_codex_bridge_gpu_snapshot`, `builtin_codex_bridge_engine_inventory`), whose engine list is derived from `main.rs`'s `engine_inventory`, the single table of built-in engine ids that `rocm examine`, `rocm update` and the `--engine` help test read as well. All three are `pub(crate)`: [`main.rs`](../apps/rocm/src/main.rs)'s `dispatch()` calls `build_codex_bridge_snapshot` through a re-import, [`chat/mcp_bridge.rs`](../apps/rocm/src/chat/mcp_bridge.rs)'s internal MCP tools reach them as `crate::<name>` through the same re-import. It has no tests of its own.
- [`chat.rs`](../apps/rocm/src/chat.rs) — the chat assistant's entry points and the module that ties its pieces together, a file beside a `chat/` directory of child modules (as [`providers.rs`](../apps/rocm/src/providers.rs) is beside `providers/`). It keeps `read_piped_prompt` and `piped_prompt_from_input` (the `echo "…" | rocm chat` path), `render_chat_text` (the status screen), `render_chat_prompt_text` (the one-shot reply text, which calls into `chat/turn.rs`), `plain_provider_auth_status` and the clap value parsers for the sampling flags (`parse_non_negative_temperature`, `parse_unit_interval`, `parse_positive_u32`), plus the re-exports below. The work behind them lives in four leaf children: [`chat/turn.rs`](../apps/rocm/src/chat/turn.rs) (the turn loop, the system prompt and the transcript), [`chat/intent.rs`](../apps/rocm/src/chat/intent.rs) (the prompt-intent heuristics), [`chat/mcp_bridge.rs`](../apps/rocm/src/chat/mcp_bridge.rs) (the MCP tool bridge and in-process command execution) and [`chat/summaries.rs`](../apps/rocm/src/chat/summaries.rs) (the deterministic tool-output summaries); `turn` is the top of that call graph and calls the other three, none of which calls back. The tool-call validation and approval policy (`validate_chat_tool_call`, the `validate_chat_*_tool_call` family, `ChatRocmCommandAction`, `ChatToolApprovalRequest`) lives in [`tool_policy.rs`](../apps/rocm/src/tool_policy.rs), which the children call into. Callers in other modules, production and test-only, reach the moved items through the `chat::` module boundary, so `chat.rs` re-exports each one another module reads: `run_internal_mcp_call` (`main.rs`, `dash_seam.rs`), `rocm_chat_tool_system_prompt_for_host` (`dash.rs`), `chat_tool_approval_request`, `chat_tool_call_is_read_only` and `validate_chat_tool_call` (`dash_seam.rs`), `any_substring` and `ensure_flag` (from `prompt_text.rs` and `rocm_argv.rs`, for `freeform_answer.rs` and `freeform_execution.rs`), and, only under `#[cfg(test)]`, `deterministic_comfyui_tool_summary` (`comfyui.rs`'s tests, unix only), `ChatRocmCommandAction`, `rocm_chat_tool_requested_args`, `chat_install_driver_action` and `chat_rocm_command_action_from_args` (`driver_plan.rs`'s and `system_packages.rs`'s tests). Each child's tests live in its own `mod tests`, with their original names; the two piped-prompt tests and the command-preview property tests (which drive the tool-call guards, the planner's guards and the rendered command lines across the policy, the bridge and the turn loop) stay in `chat.rs`. `serve_negative_sampling_space_form_reaches_range_validator`, a shared clap value-parser wiring test living alongside its sibling command-parsing tests, has moved with them to the test module in [`cli.rs`](../apps/rocm/src/cli.rs); the four structural checks that read [`chat_cmd.rs`](../apps/rocm/src/chat_cmd.rs)'s source for the `Command::Chat` handler's wiring (`command_chat_interactive_routes_to_dash_run_chat_not_tui`, `command_chat_interactive_notes_dropped_provider_flag`, `command_chat_honors_chat_mock_and_keeps_prompt_passthrough`, `command_chat_reads_prompt_from_piped_stdin`) live in that module's own `mod tests`.
- [`chat/turn.rs`](../apps/rocm/src/chat/turn.rs) — mechanical relocation out of `chat.rs`, a child of `chat.rs` and the top of its call graph: the chat turn loop and transcript. `render_chat_prompt_result_with_progress` is the entry point: it picks the assistant model, answers an install request that names no folder with the folder-needed text, builds the system prompt, asks the provider (or takes a tool call the intent heuristics propose when no model server is ready), runs the read-only tool calls the reply requests through the bridge, summarizes their output (through `chat/summaries.rs`, or by asking the local model for a follow-up) and renders the transcript, returning a `ChatPromptResult` (the rendered text and the approval request, if the assistant asked for a change). It owns `ChatPromptResult` and `ChatToolRunResult`, the system prompt (`ROCM_CHAT_TOOL_SYSTEM_PROMPT`, which `rocm_chat_tool_system_prompt` joins to the compiled-in assistant skill at `skills/rocm-cli-assistant/SKILL.md`, and `rocm_chat_tool_system_prompt_for_host`, which grounds it in the machine it answers for), `append_chat_tool_results` and the helpers around it (the `local_*` decisions about intermediate and final replies and the missing-service text, `deterministic_mutating_tool_call_for_prompt` and `supplemental_read_only_tool_call_for_prompt`, the tool-call display labels, `mcp_tool_result_is_error`, `visible_chat_content` which strips reasoning blocks, and `render_install_sdk_folder_needed_chat_text`). `render_chat_prompt_result_with_progress` and `ChatPromptResult` are `pub(super)` (called from `chat.rs`), `rocm_chat_tool_system_prompt_for_host` is `pub(crate)` and re-exported from `chat.rs` for `dash.rs`, and the rest is private. Its edges out are `chat/intent.rs`, `chat/mcp_bridge.rs`, `chat/summaries.rs`, `tool_policy.rs`, `rocm_argv.rs`, `freeform_planner.rs` (`format_structured_tool_call`), `engine_runtime_select.rs`, `managed_service_status.rs`, `chat_host_facts.rs` and `providers`; nothing below it calls back. Most of the former `chat.rs` tests moved with it into its own `mod tests`, with their original names.
- [`chat/summaries.rs`](../apps/rocm/src/chat/summaries.rs) — full domain extraction, a leaf child of `chat.rs`: the deterministic summaries of the read-only tool output the assistant reads back. `deterministic_chat_tool_summary` is the entry point the turn loop calls; it tries `deterministic_rocm_tool_summary` (`examine`), `deterministic_model_tool_summary` (model recipes, with `deterministic_engine_fit_summary` and `deterministic_available_engine_names`) and `deterministic_combined_status_tool_summary` (ComfyUI, port status, engine inventory and services, via the `deterministic_*_tool_summary` functions) in that order, and `deterministic_summary_can_stand_alone` says whether a summary may replace the model's own follow-up. The row types and parsers behind them (`DeterministicModelRecipe`, `DeterministicServiceRow`, `DeterministicEngineRow`, the `parse_deterministic_*` functions and their line helpers), `chat_tool_value` and `managed_service_running_state`, the status-to-running-state mapping that the services tool text in `chat/mcp_bridge.rs` also uses, live here too. `deterministic_chat_tool_summary`, `deterministic_summary_can_stand_alone` and `managed_service_running_state` are `pub(super)`, called from `chat/turn.rs` (and `chat/mcp_bridge.rs` for the last); `deterministic_rocm_tool_summary` is `pub(super)` for `chat/turn.rs`'s tests, and `deterministic_comfyui_tool_summary` stays `pub(crate)` for `comfyui.rs`'s tests, reached through `chat.rs`; the rest is private. Its only edges out are `providers` (the assistant model ids), `managed_service_status::friendly_engine_label` and `rocm_core::placeholder::empty_as_unknown`; nothing here calls back into `chat.rs`. The tests of the parsers, `managed_service_running_state` and the summary builders that need no chat turn live in this module's own `mod tests`; the tests that run a summary through the turn loop's follow-up decision stay in `chat/turn.rs`.
- [`chat/mcp_bridge.rs`](../apps/rocm/src/chat/mcp_bridge.rs) — mechanical relocation out of `chat.rs`, a leaf child of `chat.rs`: the MCP bridge and in-process command execution behind the assistant's tools. `run_internal_mcp_call` is the tool dispatch (`rocm mcp-call`, the dash execution seam and the assistant's read-only path all end in it): it validates the call through `tool_policy.rs`, refuses a state-changing tool unless mutation was allowed, then runs the tool in process or hands an approved `rocm` command to a child process. `run_rocm_read_only_in_process` is the in-process runner for the read-only `rocm` commands the assistant may ask for, `run_rocm_command_for_paths` and `run_rocm_capture_for_paths` wrap a command's output as a `CommandCapture`, and `internal_mcp_arguments`, `internal_mcp_tool_success` and `internal_mcp_tool_result_from_command` build the MCP tool result, and `mcp_tool_result_text` reads the text back out of one. - [`amd_smi.rs`](../crates/rocm-core/src/amd_smi.rs) — (ROCMAI-723) locating the `amd-smi` binary: `resolve_amd_smi_binary` (re-exported at the crate root) prefers the newest managed ROCm SDK runtime recorded in the registry, then the home-directory venv and legacy locations, then the bare name for a `PATH` lookup. It only reads the registry records [`managed_runtime.rs`](../crates/rocm-core/src/managed_runtime.rs) exposes and [`runtime.rs`](../crates/rocm-core/src/runtime.rs)'s data/home directory lookups. As of EAI-8457 it also owns the *launch*: `amd_smi_json` (also re-exported at the crate root) is the one supported way for a synchronous caller to run `amd-smi`, because it is the only place the mandatory `/dev/kfd` pre-flight runs (`KFD_DEVICE`, `preflight_kfd_device`, `kfd_readable`/`kfd_readable_with`, and the thread-bounded, budget-capped `device_readable`/`device_readable_within_budget` probe behind `KFD_OPEN_TIMEOUT`). The crate's remaining top-level modules, besides `agent/`, `app/` and `ui/`:

- [`client.rs`](../crates/rocm-dash-tui/src/client.rs) — the connection task behind the dashboard's event stream, and `ClientMsg`, the one message type the app loop reads. `spawn` loops forever: it posts `Connecting`, runs `connect_and_run`, posts `Disconnected`, then sleeps for the next delay from [`reconnect.rs`](../crates/rocm-dash-tui/src/reconnect.rs) before trying again. On unix `connect_and_run` takes a `unix:/path` address (any other scheme is rejected), reads the daemon's `Welcome`, sends `Hello` and `Subscribe`, and forwards each event until `Bye` or EOF. On Windows there is no daemon socket, so the `cfg(windows)` arm collects host and GPU metrics in-process once a second through `rocm-dash-collectors` (the only use of that dependency) and posts them as `ClientMsg::HostGpuSnapshot`, which `AppState::push_host_gpu_snapshot` applies without treating its empty instance list as authoritative. Besides daemon events, `ClientMsg` carries the replay position and the TUI-internal chat, slash-command and approval results that [`replay.rs`](../crates/rocm-dash-tui/src/replay.rs) and the `agent/` and `app/` modules post.
- [`jobs.rs`](../crates/rocm-dash-tui/src/jobs.rs) — the one async process runner every operational screen shares. `run_effects` takes the `SideEffect`s the pure reducer in `rocm-dash-core` returns and starts a task for each `SideEffect::SpawnJob`. The task spawns the child with null stdin and piped stdout and stderr (`kill_on_drop`), posts each line as `StateEvent::JobLine` (keeping only the last `\r`-separated segment, so a progress bar that redraws in place reads as one line), and, once both pipes have closed, finishes with `JobDone` (the exit code, -1 when the child has none, as when a signal killed it) or `JobErr` for a wait failure; a spawn failure posts `JobErr` at once. It checks the shared cancel flag after every line and at least every 100 ms (`CANCEL_POLL`) while the child is idle, and kills the child when it flips; a cancelled job posts neither, because the reducer has already marked it `Cancelled`. Events go back over an unbounded channel on purpose: the reducer is synchronous and cannot apply backpressure, so output is bounded in the reducer instead (`JOB_OUTPUT_RING_CAP`). `app/event_loop.rs` owns the channel and folds the events into `AppState::jobs`; the screens in `ui/` start jobs only through `StateEvent::StartJob`.
- [`lib.rs`](../crates/rocm-dash-tui/src/lib.rs) — the library root: declares `agent`, `app`, `client`, `jobs`, `llm`, `reconnect`, `registry_probe`, `replay`, `tool_exec`, `transport` and `ui` as public modules, so `apps/rocm` runs the dashboard through `app::run` and the examples and integration tests drive the same modules in-process.
- [`llm.rs`](../crates/rocm-dash-tui/src/llm.rs) — chat endpoint configuration, with no HTTP client (the Rig-backed agents are in [`agent/clients.rs`](../crates/rocm-dash-tui/src/agent/clients.rs)). `resolve_llm_config` is a pure resolver: the base URL comes from the CLI, else the config, else the environment, else `DEFAULT_CHAT_BASE_URL` only if a TCP probe of it succeeded, and it returns `None` when none applies; the model comes from the CLI, else the config, else `DEFAULT_CHAT_MODEL`. `resolve_llm_config` strips the API key and custom auth header from a loopback base URL (`parse_host_port` handles bracketed IPv6, then `is_loopback_host`) and logs a warning when it discards one, so a configured local endpoint is never sent a gateway credential, and `LlmConfig`'s `Debug` redacts the key. `probe_endpoint(url, timeout)` is a TCP-only liveness check, and its callers pass `PROBE_TIMEOUT` (300 ms) for each resolved address, and `detect_local_endpoint` probes the Lemonade, vLLM and `rocm serve` default endpoints concurrently and returns the highest-priority one that answered; the last port is a literal copy of `rocm-core`'s default because this crate cannot depend on it. `pick_first_model` reads the first id of a `/v1/models` reply, which `apps/rocm`'s `dash.rs` also calls. The chat code in `app/chat_runtime.rs`, `app/chat.rs` and the Chat tab uses it.
- [`reconnect.rs`](../crates/rocm-dash-tui/src/reconnect.rs) — `Backoff`, the exponential delay `client.rs` sleeps between connection attempts: 250 ms, doubling up to 10 s, started over (a new `Backoff::default()`) after a connection that ended cleanly.
- [`registry_probe.rs`](../crates/rocm-dash-tui/src/registry_probe.rs) — the seam through which the dashboard reads the managed-service registry without depending on `rocm-core` or the daemon. `ManagedRegistryProbe::snapshot` returns a `ManagedRegistrySnapshot`: whether any record is live, and the ids `rocm services stop <id>` can reach. The binary implements it (`LiveManagedRegistryProbe` in `apps/rocm`'s `dash.rs`) and hands it in on `ResolvedArgs`. It is read live, at each quit attempt and each frame the quit-confirm prompt is open, rather than once at launch, so a model started mid-session and a Windows host with no instance snapshot are both seen; implementations must stay cheap (a local file read). It answers from each record's own status, so it can lag `rocm services list`, which also checks process liveness. `StaticManagedRegistrySnapshot` wraps an already-read snapshot for the launcher, which reads the registry once per menu pass. Compare [`tool_exec.rs`](../crates/rocm-dash-tui/src/tool_exec.rs), the same pattern for tool calls.
- [`replay.rs`](../crates/rocm-dash-tui/src/replay.rs) — the offline source behind `--replay`. `spawn` starts a task that posts `Connecting`, reads the whole session file up front (NDJSON `PersistedEntry` lines; a malformed line is skipped with a warning), posts `Connected`, and then posts the recorded events through the same `ClientMsg` channel as `client.rs`, so nothing downstream tells replay from a live daemon; it ends in `Disconnected` (the read error, or "end of recording"). `app/event_loop.rs` starts replay when `--replay` is given and the live client otherwise, except that a focused host without `--replay` starts neither. Between events it sleeps for the recorded gap capped at 2 s (`MAX_GAP_MS`) and then divided by the speed, with a 1 ms floor, so the cap bounds the recorded gap and not the wall-clock wait: at 0.25x a long gap sleeps 8 s. The returned `ReplayController` is what `app/actions.rs` drives: pause, resume, speed (`SPEED_STEPS`, 0.25x to 8x, stepped by `next_speed`/`prev_speed`) and jump. A forward jump emits the events it crosses at once; a backward jump posts `ClientMsg::ReplaySeek`, so the app drops state derived from past events, then re-emits from the start up to the new position. Every emitted event is followed by `ClientMsg::ReplayPosition` for the header's elapsed/total readout.
- [`tool_exec.rs`](../crates/rocm-dash-tui/src/tool_exec.rs) — the seam for chat tool calls that need `rocm-core`, in plain `serde_json` types. `RocmToolExecutor::execute` runs a read-only tool and returns `RocmToolOutcome::Result`, or returns `ApprovalRequired(ApprovalIntent)` for a mutating one without running it, or `Error`. `execute_approved` runs the same `(name, arguments)` only after the operator approves, re-validating first, and blocks, so callers run it off the async loop. The binary implements the trait (`BinToolExecutor` in `apps/rocm`'s `dash_seam.rs`); the dashboard holds it as `SharedRocmToolExecutor`, `None` under demo, replay and mock. The chat tools and slash commands use it; the operational screens in `ui/` do not, they spawn the `rocm` binary themselves through [`jobs.rs`](../crates/rocm-dash-tui/src/jobs.rs).
- [`transport.rs`](../crates/rocm-dash-tui/src/transport.rs) — newline-delimited JSON framing for `client.rs`: `write_line` serializes one value plus a newline and flushes, `read_line` returns `None` at EOF and an `InvalidData` error for a line that is not valid JSON for the requested type. The daemon's [`transport.rs`](../crates/rocm-dash-daemon/src/transport.rs) holds the same two functions, copied rather than shared so this crate does not depend on the daemon; the two sides serialize the `rocm-dash-core` protocol types.

Thirteen operational overlays share one lifecycle. Each has a state struct held as an `Option` on `AppState` (`None` is closed) and is opened by a `KeyAction::Open*` arm in [`app/actions.rs`](../crates/rocm-dash-tui/src/app/actions.rs), a slash command ([`app/slash.rs`](../crates/rocm-dash-tui/src/app/slash.rs)), the quit-confirm prompt's `s` key ([`app/quit_confirm.rs`](../crates/rocm-dash-tui/src/app/quit_confirm.rs)) or the startup focus ([`app/focus.rs`](../crates/rocm-dash-tui/src/app/focus.rs)), each of which first calls `close_overlays`, so at most one is open. `draw_active_manager` in [`ui/mod.rs`](../crates/rocm-dash-tui/src/ui/mod.rs) draws it into a centered card over a dimmed backdrop and shows the shared [job console](../crates/rocm-dash-tui/src/ui/job_console.rs) instead once the overlay's `active_job` is set. A screen's `on_key` mutates its own state and the shared job `State` and returns the reducer's `SideEffect`s, which `app/event_loop.rs` runs through [`jobs.rs`](../crates/rocm-dash-tui/src/jobs.rs). A mutating action stages an `ApprovalRequest` held in the screen's own state and shown by [`ui/approval.rs`](../crates/rocm-dash-tui/src/ui/approval.rs); the `rocm` path is resolved with `resolve_exe` when it is staged, the job starts only on Approve, and the CLI does the mutation, so the dashboard changes nothing itself. Read-only actions start their job directly. That is a separate path from a chat tool call's approval (`AppState::approval`, [`app/tool_approval.rs`](../crates/rocm-dash-tui/src/app/tool_approval.rs)). Exceptions are noted per screen.

The other three dashboard crates each have a crate-level bullet, followed by a bullet for each source file the crate-level bullet does not already name:

- [`rocm-dash-collectors`](../crates/rocm-dash-collectors/src/lib.rs) — the IO-heavy collector implementations behind `rocm-dash-core`'s traits (amd-smi, Docker, host metrics, Lemonade and vLLM scrapers, and on Windows the [`winperf.rs`](../crates/rocm-dash-collectors/src/winperf.rs) perf-counter/ADLX GPU collector) plus the benchmark load generator; used by `rocm-dash-daemon` and, on Windows, by `rocm-dash-tui` in-process.
  - [`amd_smi.rs`](../crates/rocm-dash-collectors/src/amd_smi.rs) — the amd-smi collector. `AmdSmiCollector::detect_with_binary` returns `Some` only when a pre-flight passes and `amd-smi version` answers in time; its async methods (`metrics`, `power_limits`, `processes`, `system_info`) run `amd-smi ... --json` under a timeout with `kill_on_drop` and pass the output to pure parsers (`parse_metrics`, `parse_power_limits`, `parse_processes`, `parse_system_info`) that tolerate differences between amd-smi releases and return an empty or default value for a shape they do not recognise. The pre-flight exists because amd-smi can block in uninterruptible kernel sleep on a host with no readable `/dev/kfd`: unless the caller says the GPU is already known to be reachable without one (a verdict `apps/rocm` computes once, true only on WSL with a usable GPU, and hands to the daemon through `RunnerOptions`), it runs `rocm_core::device_readable_bounded` on the blocking pool. `detect_with_binary_skipping_device_preflight` exists for tests that point at a fake script.
  - [`bench_load.rs`](../crates/rocm-dash-collectors/src/bench_load.rs) — the concurrency-sweep load generator behind `rocm bench load`, reached through `rocm_dash_daemon::bench_load`. `run_cell` sends `LoadSpec.requests` chat-completion requests at one concurrency and returns a `CellReport`: the `BenchmarkRow` plus attempted, succeeded and failed counts, the first error and an optional `EngineSplitNotice`. `run_and_append_csv` and `run_auto_ramp` (which walks `RAMP_SEQUENCE` and stops after the last level, on a throughput plateau against the previous cell, or when the queue is backed up, `should_stop_ramp`) append each cell to a CSV, taking an exclusive file lock for each row, and refuse a file whose first line differs from `CSV_HEADER` when the first row is appended. During a cell it scrapes the endpoint's Prometheus `/metrics` with a short timeout and sets the row's `engine` only when the scrape is recognisably vLLM; because `engine` is a rollup key, appending a row that carries an `engine` to a file that already holds blank-`engine` rows for that cell is reported, once per sweep, through `EngineSplitNotice` for the CLI to print, not printed here.
  - [`bench_tail.rs`](../crates/rocm-dash-collectors/src/bench_tail.rs) — `CsvBenchTailer`, the `BenchTailer` the daemon runner uses on the configured benchmark CSV. Each `drain()` re-reads the whole file and returns only the rows past the count it has already returned, resets that count (and so re-emits every row) only when the file now has fewer rows than before, so a rewrite that is not shorter goes undetected, and returns nothing while the file does not exist; a row that fails to parse makes that drain return an error. Re-reading avoids tracking offsets and inodes, which is affordable because benchmark CSVs are small.
  - [`cgroup.rs`](../crates/rocm-dash-collectors/src/cgroup.rs) — attributing GPU processes to containers. `parse_container_id_from_cgroup` is a pure scan of `/proc/<pid>/cgroup` text for the first run of exactly 64 lowercase hex characters (cgroup v1, v2 and containerd layouts), `container_id_for_pid` reads that file (Linux only; a stub returns `None` elsewhere) and `is_container_id` tests the shape. amd-smi reports host PIDs and a tensor-parallel server's workers are descendants of the container's init process, so the join goes through the cgroup and not through PID equality; a managed `rocm serve` service id never has this shape, so such a service can never be a key of the per-container VRAM map.
  - [`docker.rs`](../crates/rocm-dash-collectors/src/docker.rs) — `DockerDiscovery`, discovery through `bollard`. `detect` returns `Some` only when the local Docker daemon answers a ping within two seconds; `discover_async` lists running containers whose image matches the glob-style patterns (default `vllm/*` and `rocm/vllm*`, `*` being the only wildcard) and inspects each under a timeout; `parse_container` builds the `DiscoveredService` from the container's environment and command line: GPU ids from `HIP_VISIBLE_DEVICES` (unless it is empty or `all`), else the first non-empty of `AMD_VISIBLE_DEVICES`, `ROCR_VISIBLE_DEVICES` and `CUDA_VISIBLE_DEVICES`, tensor-parallel size, dtype, quantization (falling back to `--dtype`), model name and a published host port taken from an unordered map of bindings (so with several published ports which one is used is arbitrary; default 8000). Docker gives no readiness signal, so a discovered container is `InstanceStatus::Starting` with no phase. The sync `ServiceDiscovery::discover` returns `Unsupported`.
  - [`engine_registry.rs`](../crates/rocm-dash-collectors/src/engine_registry.rs) — `EngineKind` (`Vllm`, `Lemonade`) maps an engine to its label, conventional port and sample parser: `label` and `from_label` (case-insensitive), `default_port` (a fallback only; a managed service's port comes from its registry record) and `parse_sample`, which dispatches to `vllm_prom::parse` or `lemonade::parse_stats`. In production only `label` and `from_label` are called: the daemon's `registry.rs` reaches `from_label` through `engine_kind_for` to leave managed records that are not vLLM out of the vLLM scrape, and `bench_load.rs` takes the `vllm` label so the CSV `engine` column cannot drift from the registry's spelling. `default_port` and `parse_sample` are exercised only by tests, since the runner builds its collectors directly.
  - [`host.rs`](../crates/rocm-dash-collectors/src/host.rs) — `HostCollector`, CPU (overall and per core), memory and swap from `sysinfo`, sampled once per tick into `SystemMetrics`; the constructor primes the CPU counters because the first reading is meaningless. Disk and network rates are not collected yet and are always reported as zero. It is cross-platform, and `rocm-dash-tui` also runs it in-process on Windows, where there is no daemon socket.
  - [`lemonade.rs`](../crates/rocm-dash-collectors/src/lemonade.rs) — the Lemonade Server collector. The parsers are pure: `parse_stats` maps `/api/v1/stats` `tokens_per_second` to `gen_tps` (Lemonade reports a rate, not a counter, and no KV-cache or request-queue figures) and `parse_health_model` reads the loaded model name from `/api/v1/health`; a body that is not a JSON object parses as empty. `LemonadeCollector::discover` builds a `DiscoveredService` (synthetic `lemonade-<host>-<port>` id, status `Ready`) only when `/api/v1/health` answers, and `LEMONADE_PORT` (13305) is the fallback port. The daemon runs it only when `RunnerOptions::enable_lemonade` is set; it defaults to false and the embedded daemon that `rocm dash` starts leaves it off.
  - [`parallel.rs`](../crates/rocm-dash-collectors/src/parallel.rs) — `parallel_scrape`, which runs an async closure against every target concurrently on a `JoinSet` and returns `(target, result)` pairs in completion order, not input order, leaving out a task that panics; the daemon runner uses it for the per-instance vLLM `/metrics` scrapes.
  - [`vllm_prom.rs`](../crates/rocm-dash-collectors/src/vllm_prom.rs) — the vLLM `/metrics` scraper. `VllmPrometheusCollector::fetch_async` GETs `http://<host>:<port>/metrics` for a service's port and `parse` (crate-private; reached through `EngineKind::parse_sample` and by `bench_load.rs`) reads the running and waiting request gauges, KV-cache usage (rescaled from 0..1 to 0..100) and the cumulative generation-token counter and TTFT and TPOT histogram sums and counts, each from the first matching sample line (label sets are not summed). It leaves `gen_tps` empty because vLLM uses the counter path: the runner differences the counters into rates. The sync `InstanceMetrics::fetch` returns `Unsupported`.
- [`rocm-dash-core`](../crates/rocm-dash-core/src/lib.rs) — pure types, traits, schemas and the reducer, with no rendering dependencies. [`chat_template.rs`](../crates/rocm-dash-core/src/chat_template.rs) also holds the chat-template defaults a locally served model needs on a chat request (`local_model_should_disable_thinking`), kept here as the leaf crate both front ends already depend on so that `apps/rocm`'s [`providers/wire.rs`](../apps/rocm/src/providers/wire.rs) and the TUI's [`agent/clients.rs`](../crates/rocm-dash-tui/src/agent/clients.rs) cannot drift apart on it.
  - [`bench_rollup.rs`](../crates/rocm-dash-core/src/bench_rollup.rs) — Pass^N / Pass@N rollups: `rollup_pass_n` groups rows into trial sets keyed by `(cell, model, engine, tp, dtype, concurrency)` and returns one `PassNRollup` per group, sorted by that key, with a strict verdict (all N trials passed), a lenient one (at least one passed) and mean prompt and generation throughput; `row_verdict` falls back from `pass_fail` to the judge verdict when the rollup is `Unknown`. Because `engine` is in the key, rows with a blank `engine` do not group with rows that have one. It is pure, and the Bench tab ([`ui/tabs/bench.rs`](../crates/rocm-dash-tui/src/ui/tabs/bench.rs)) and the agent's telemetry helpers ([`agent/snapshot.rs`](../crates/rocm-dash-tui/src/agent/snapshot.rs)) recompute it from the rows rather than reading the CSV's `pass_n_of_n` and `pass_at_n` columns.
  - [`bench_schema.rs`](../crates/rocm-dash-core/src/bench_schema.rs) — `BenchmarkRow`, the one row type for a benchmark result (identity, platform, backend configuration, request statistics, throughput, latency, quality, rollup and provenance columns), and `PassFail`. Almost every field is an `Option` and the struct is `#[serde(default)]`, so a CSV or a recording that omits columns still deserializes. `CsvBenchTailer` deserializes CSV rows into it, `bench_load.rs` builds it, and the daemon forwards it in `Event::BenchmarkRowsAppended`.
  - [`config.rs`](../crates/rocm-dash-core/src/config.rs) — the standalone dashboard configuration read from `<config dir>/rocm-dash/config.toml` (`default_config_path`; a missing file means defaults and `Config::load` fails only on a read or parse error): `Config` with `DaemonConfig` (listen address, token, tick intervals, benchmark CSV path), `TuiConfig` (connect address, theme, chat endpoint, model and auth-header name) and per-engine `EngineConfig`. It is separate from the unified `rocm` configuration (the `dashboard` section of `rocm-core`'s `RocmCliConfig`, which `rocm dash` reads); in the tree only the TUI's chat-endpoint save (`persist_chat_endpoint` in [`app/chat.rs`](../crates/rocm-dash-tui/src/app/chat.rs)) loads and writes this file. Its default socket path (`$XDG_RUNTIME_DIR`, then `~/.rocm/data/telemetry`, then a user-named directory under the temp dir) is a copy of `rocm-core`'s on purpose, because this crate may have no first-party dependencies (`cargo xtask check-crate-edges` enforces that).
  - [`efficiency.rs`](../crates/rocm-dash-core/src/efficiency.rs) — the pure join of throughput and power. `normalize_gpu_id` strips the `gpu-` prefix so the bare indices Docker discovery records in `Instance.gpu_ids` match amd-smi's `gpu-N` device ids; `attribute_power_w` splits each GPU's board power among the instances that occupy it, weighted by per-container VRAM, equally when any occupant has no reading, and yields `None` for an instance none of whose GPUs reported a positive power reading; `tokens_per_watt` divides generation throughput by that attributed power. The daemon runner calls `attribute_power_w`, `tokens_per_watt` and `gpu_ids_overlap`, which it uses to warn when the id join finds nothing.
  - [`metrics.rs`](../crates/rocm-dash-core/src/metrics.rs) — the live metric types every other dashboard crate shares: `Snapshot` (one tick: `SystemMetrics`, a `GpuMetrics` per GPU, an optional `GpuSystemInfo`, the `Instance` list and warnings), `Instance` with its `InstanceStatus` (`Starting` carries an optional `StartupPhase`; `is_serving`, `is_starting`, `counts_as_running` and `label` are the one definition of those predicates and chip labels) and `ObservationMetadata`/`ObservationFreshness`, which mark a throughput or latency value as freshly measured or held over from an earlier scrape. The optional fields added after the first recordings (`power_limit_w`, `gen_tps`, `tokens_per_watt`, `power_w`, `ttft_ms`, `tpot_ms` and the three `*_observation` fields) are `#[serde(default)]`, so older recordings still deserialize.
  - [`observation.rs`](../crates/rocm-dash-core/src/observation.rs) — how a generation-throughput counter becomes a rate that stays honest. `GenerationObservationTracker` keeps a bounded window of counter samples, computes a rate over `rate_window(instance_tick)` (`clamp(5 x tick, 10 s, 30 s)`), reports the value as fresh or held for up to `observation_validity(instance_tick)` (`clamp(3 x tick, 6 s, 30 s)`), clears on a counter reset or on expiry, and accepts a rate an engine reports directly through `observe_direct`. All time is passed in, so the module reads no clock. The runner keeps one tracker per instance for throughput and one each for TTFT and TPOT; it drops them when a service is retired and calls `invalidate` when a service's port changes under the same id.
  - [`partition.rs`](../crates/rocm-dash-core/src/partition.rs) — the `ComputePartitionMode` (`Spx`, `Dpx`, `Qpx`, `Cpx`) and `MemoryPartitionMode` (`Nps1`, `Nps2`, `Nps4`) enums, each defaulting to `Unknown` and serialized in upper case. `GpuSystemInfo` in `metrics.rs` holds them and `amd_smi.rs` parses them from amd-smi output.
  - [`persist.rs`](../crates/rocm-dash-core/src/persist.rs) — `PersistedEntry`, one recorded `Event` plus its `ts_us` (microseconds since the epoch): the daemon stamps wall-clock time, the demo generator a fixed synthetic one. The daemon's [`persist.rs`](../crates/rocm-dash-daemon/src/persist.rs) writes one per NDJSON line, the demo generator emits the same format, and the TUI's [`replay.rs`](../crates/rocm-dash-tui/src/replay.rs) reads them back and paces playback by the `ts_us` gaps, each capped at 2 s and then divided by the playback speed.
  - [`protocol.rs`](../crates/rocm-dash-core/src/protocol.rs) — the NDJSON wire protocol between the daemon and a TUI client: `Command` (client to daemon: `Hello`, `Subscribe`, `RequestSnapshot`, `RescanInstances`, `Pause`, `Resume`, `Goodbye`) and `Event` (daemon to client: `Welcome`, `Snapshot`, `InstanceDiscovered`, `InstanceGone`, `BenchmarkRowsAppended`, `Warning`, `Error`, `Bye`), both internally tagged with `kind`, and `PROTOCOL_VERSION`, which is bumped when the JSON shape of an existing variant changes. Internal tagging rejects a newtype variant that wraps a sequence, so every `Event` variant is a struct variant or wraps a struct, and a test round-trips each variant to hold that.
  - [`state.rs`](../crates/rocm-dash-core/src/state.rs) — the pure reducer, `State::apply(StateEvent) -> Vec<SideEffect>`, holding the latest snapshot, a bounded history (`SNAPSHOT_RING_CAP`), instances keyed by container id, bounded benchmark rows (`BENCH_RING_CAP`), the paused flag and the background-job table (`JobState`/`JobStatus`, output bounded by `JOB_OUTPUT_RING_CAP`), with no tokio or ratatui types. `JobStatus::glyph`, `label` and `legend_glyphs` are the one definition of how a job status is drawn. It has two kinds of user: the daemon runner applies `Tick`, `InstanceUpserted`, `InstanceRemoved` and `BenchmarkRows`, discards the returned effects and reads back only the instance map, and the TUI keeps one `State` for all of its jobs, `AppState::jobs`: `app/event_loop.rs` passes `&mut state.jobs` to the key handler of every screen that runs `rocm` commands (for example [`ui/update_manager.rs`](../crates/rocm-dash-tui/src/ui/update_manager.rs) and [`ui/runtime_manager.rs`](../crates/rocm-dash-tui/src/ui/runtime_manager.rs)), applies the job events that come back from [`jobs.rs`](../crates/rocm-dash-tui/src/jobs.rs) to that same instance, and runs the `SideEffect::SpawnJob`s the handlers return through `jobs.rs`. The table outlives any one overlay: closing a screen leaves its jobs in it. Only `SpawnJob` is interpreted: the `Persist` and `Broadcast*` effects are produced but nothing consumes them.
  - [`traits.rs`](../crates/rocm-dash-core/src/traits.rs) — the collector-side contracts and the data they exchange: `DiscoveredService` (a found serving process or container), `InstanceSample` (one scrape's KV-cache usage, request counts, cumulative token counter and latency-histogram sums, or a rate the engine reports directly), `GpuProcess`, `CollectorError`, and `merge_instance`, which turns a service, a sample and VRAM figures into an `Instance`, copying a directly reported `gen_tps` and leaving `tokens_per_watt`, `power_w`, TTFT, TPOT and the freshness fields `None` for the runner to fill. The traits are synchronous, and the runner calls only `BenchTailer::drain`, on a concrete `CsvBenchTailer`; the Docker and vLLM-Prometheus implementations of `ServiceDiscovery` and `InstanceMetrics` return `CollectorError::Unsupported`, because their real API is the async inherent methods `discover_async` and `fetch_async`.
  - [`vram.rs`](../crates/rocm-dash-core/src/vram.rs) — the pure VRAM attribution maths. `aggregate_process_vram` folds per-process readings into a per-container map through an injected PID-to-container resolver (the runner passes `cgroup::container_id_for_pid`), and `resolve_instance_vram` returns an instance's `(used, total)`: the per-container figure when there is one, otherwise the device-summed used over its GPUs, with `total` always device-summed and `(0, 0)` for an instance with no map entry and no matching GPU. It reuses `efficiency.rs`'s id matching and does no `/proc` or process I/O.
- [`rocm-dash-daemon`](../crates/rocm-dash-daemon/src/lib.rs) — the daemon library: [`runner.rs`](../crates/rocm-dash-daemon/src/runner.rs) drives the collectors on tick cadences and broadcasts snapshots, and [`server.rs`](../crates/rocm-dash-daemon/src/server.rs) streams them to TUI clients as NDJSON. [`registry.rs`](../crates/rocm-dash-daemon/src/registry.rs) reads the managed-service records `rocm serve` writes and tells a registry that is confirmed empty (no directory, or no records) from one that could not be read: the run loop retires a managed service that an empty registry lacks, but when a pass cannot read the registry in full (a directory that cannot be listed, or a record file that cannot be opened) it retires nothing: the known services and their data stay, as when Docker discovery errors, the records that did read still add and refresh their services, and the header warns until a read succeeds. `apps/rocm`'s [`dash.rs`](../apps/rocm/src/dash.rs) drives it.
  - [`bench_ring.rs`](../crates/rocm-dash-daemon/src/bench_ring.rs) and [`snapshot_ring.rs`](../crates/rocm-dash-daemon/src/snapshot_ring.rs) — the daemon's two bounded histories for late-joining clients, `BenchRing` (200 rows) and `SnapshotRing` (30 snapshots), each a `VecDeque` that drops its oldest entry when full. On `Command::Subscribe`, `server.rs` replays the snapshot ring one `Snapshot` event at a time, then the benchmark ring as a single `BenchmarkRowsAppended` event (if it holds any rows), to that client before it sends live events.
  - [`demo.rs`](../crates/rocm-dash-daemon/src/demo.rs) — the synthetic-session generator behind `rocm dash --demo`. `generate_to_writer` and `generate_file` write a recording as `PersistedEntry` lines (a `Welcome`, one `Snapshot` per simulated second, the instance discoveries on the first tick, scheduled benchmark rows and a closing `Bye`) of an 8-GPU node serving three vLLM containers, so the dashboard replays populated data with no GPU and no daemon. The same `DemoOptions` (seconds and seed) produce byte-identical output, from seeded jitter and a fixed wall-clock anchor; the file is created `0o600` on Unix (an existing file keeps its mode) and removed again if generation fails.
  - [`persist.rs`](../crates/rocm-dash-daemon/src/persist.rs) — `SessionWriter`, the append-only session recorder. `server.rs` opens one `session-YYYYMMDD-HHMMSS.ndjson` for the daemon's lifetime when `RunnerOptions::persist_dir` is set, which `rocm dash` always does, to the `telemetry` directory under the data dir; if the file cannot be created, persistence is switched off with a warning. Every broadcast `Event` is appended as a `PersistedEntry` line and flushed to the OS (there is no fsync, and a failed write is logged and skipped), so a process crash loses at most the in-flight tick. There is no rotation or compression; the TUI's replay mode reads the file.
  - [`transport.rs`](../crates/rocm-dash-daemon/src/transport.rs) — NDJSON framing for the daemon's socket: `write_line` serializes a value as one JSON line and flushes, `read_line` reads one line and returns `None` at end of input. [`rocm-dash-tui/src/transport.rs`](../crates/rocm-dash-tui/src/transport.rs) is a copy of it, because the TUI does not depend on the daemon crate, so a framing change must be made in both.

### `crates/e2e-report`

Modularized (ROCMAI-60, Phase 1 of ROCMAI-27's sequencing):

- [`command_coverage.rs`](../crates/e2e-report/src/command_coverage.rs) — (ROCMAI-486, Phase 1 of a staged further split of [`consolidated/mod.rs`](../crates/e2e-report/src/consolidated/mod.rs)) the CLI command-coverage audit table — which `rocm` commands were exercised and whether they passed — consumes `consolidated::PlatformReport` but shares no type with the `Grid`/reconciliation model itself.
- [`components.rs`](../crates/e2e-report/src/components.rs) — shared maud HTML fragment rendering, plus the CSS and timestamp helpers both generators use, depending only on [`parse.rs`](../crates/e2e-report/src/parse.rs) types to keep the module graph acyclic.
- [`consolidated/mod.rs`](../crates/e2e-report/src/consolidated/mod.rs) — the `PlatformReport` model (loading one platform's `report.json` together with its sidecars), the reconciled scenario × platform `Grid`, the `PlatformReports` bundle and `load_platform_reports`, which both renderers draw from, plus the scenario-reference map it builds, and the report text both renderers share so it cannot drift between them: `LEGEND_ENTRIES` (the grid legend) and the two phrases of the PR-gating policy, `MOCK_GATES_PR` and `OTHER_LANES_NON_BLOCKING`, which the markdown explanation paragraph and the HTML legend each build their own sentence around. Artifact-name parsing lives in [`consolidated/descriptor.rs`](../crates/e2e-report/src/consolidated/descriptor.rs), the `platform.json`/`commands.jsonl` schema and parsing in [`consolidated/sidecars.rs`](../crates/e2e-report/src/consolidated/sidecars.rs) (both reached through `use`), and the two renderers in [`consolidated/html.rs`](../crates/e2e-report/src/consolidated/html.rs) and [`consolidated/markdown.rs`](../crates/e2e-report/src/consolidated/markdown.rs), declared `pub(super) mod`. It is still the largest module in the crate, still holding the `Grid`/`PlatformReport` model and the bundle in one file; what remains of the split is optional: a `grid.rs` split and a relocation of [`command_coverage.rs`](../crates/e2e-report/src/command_coverage.rs).
- [`consolidated/descriptor.rs`](../crates/e2e-report/src/consolidated/descriptor.rs) — artifact-name identity: `Descriptor` and `parse_descriptor` (artifact/directory name to platform, OS, legacy known-bugs flag and channel), driven by one `KNOWN_PLATFORMS` table that also holds the `platform.json` `platform_slug`s of each lane, so the public `artifact_name_for_platform_slug` (what [`xtask`'s e2e report](../xtask/src/e2e_report.rs) uses to name a report downloaded without its artifact directory) is the inverse of the same rows rather than a second table, plus the one platform-label rule, `full_platform_label` (platform, OS and optional channel), which `PlatformReport::label`, `GridColumn::label` and the excluded-platform caption in `Grid::build` all call, and the helpers under it, `with_paren_suffix` (also used for the sdk_version leg in `parse_descriptor`) and `fallback_descriptor`. A leaf: it imports nothing from [`consolidated/mod.rs`](../crates/e2e-report/src/consolidated/mod.rs), which reaches it through `use descriptor::{...}`; its `parse_descriptor_*` tests sit beside it.
- [`consolidated/sidecars.rs`](../crates/e2e-report/src/consolidated/sidecars.rs) — sidecar schema and parsing: the `platform.json` manifest (`PlatformManifest`, `ManifestCapability`, `PlatformVersions` with its `summary`/`platform_stack` display strings, `ManifestExpectation`, `parse_platform_manifest`) and the `commands.jsonl` record (`CommandRecord`, `parse_commands`). A leaf that uses only serde, `serde_json` and `std` (no other module of the crate) and imports nothing from [`consolidated/mod.rs`](../crates/e2e-report/src/consolidated/mod.rs), which reaches it through `use sidecars::{...}`; `CommandRecord` stays `pub(crate)` because [`command_coverage.rs`](../crates/e2e-report/src/command_coverage.rs) reads it through `PlatformReport::commands`. The parsers have no direct unit tests; they are covered through `PlatformReport::load`.
- [`consolidated/html.rs`](../crates/e2e-report/src/consolidated/html.rs) — the HTML renderer: `RunMeta` and `generate_consolidated`, with the matrix table, legend, expectation grid (`expectation_grid_html`, `pub(super)` so the cross-renderer tests in [`consolidated/mod.rs`](../crates/e2e-report/src/consolidated/mod.rs) can call it) and per-platform sections it assembles. A child of [`consolidated/mod.rs`](../crates/e2e-report/src/consolidated/mod.rs) (declared `pub(super) mod html;`), so it reads the private `PlatformReport`, `Grid`, `CellOutcome` and `PlatformReports` items defined there without any of them being widened; no production code in the parent or in the markdown renderer calls into it (only the cross-renderer tests that stay in `consolidated/mod.rs` do). Its `generate_consolidated_*` and legend tests sit beside it.
- [`consolidated/markdown.rs`](../crates/e2e-report/src/consolidated/markdown.rs) — the markdown renderer: `consolidated_summary_markdown` (the table piped into `$GITHUB_STEP_SUMMARY`), `expectation_grid_markdown` and `scenario_reference_markdown`, and the call into [`command_coverage.rs`](../crates/e2e-report/src/command_coverage.rs)'s `command_coverage_markdown` for the command-coverage table. A child of [`consolidated/mod.rs`](../crates/e2e-report/src/consolidated/mod.rs) (declared `pub(super) mod markdown;`), so it reads the private `PlatformReport`, `Grid`, `CellOutcome`, `PlatformReports` and `ScenarioReference` items defined there without any of them being widened; it does not call the HTML renderer. The tests that assert on its output sit beside it; what stays in `consolidated/mod.rs` is the cross-renderer tests (HTML and markdown over one bundle), the command-coverage tests, and tests of the grid or `PlatformReport` that use the markdown only as a probe.
- [`consolidated/test_support.rs`](../crates/e2e-report/src/consolidated/test_support.rs) — `#[cfg(test)]` fixtures (`feature_json`, `write_report`, `write_platform`, `grid_order`) shared by the `consolidated/` tests, so each module extracted from [`consolidated/mod.rs`](../crates/e2e-report/src/consolidated/mod.rs) can keep its tests beside it.
- [`parse.rs`](../crates/e2e-report/src/parse.rs) — cucumber `report.json` data model, parsing, and `@expected-failure` xfail evaluation.
- [`single_report.rs`](../crates/e2e-report/src/single_report.rs) — single-platform HTML report generation.

These modules are private `mod` declarations — [`lib.rs`](../crates/e2e-report/src/lib.rs) re-exports only the selected public API surface (`XfailReport`, `evaluate_xfail`, `scenario_results_by_id`, `generate`, `RunMeta`, `PlatformReports`, `load_platform_reports`, `artifact_name_for_platform_slug`, `generate_consolidated`, `consolidated_summary_markdown`) via `pub use` (`RunMeta` and `generate_consolidated` through `consolidated::html`, `consolidated_summary_markdown` through `consolidated::markdown`: the only child modules `lib.rs` reaches by path), so consumers reach it through the crate root rather than through module-qualified paths like `e2e_report::parse::...`. `generate_consolidated` and `consolidated_summary_markdown` take the opaque `PlatformReports` bundle [`load_platform_reports`](../crates/e2e-report/src/consolidated/mod.rs) returns (ROCMAI-484 / ROCm/rocm-cli#640) — bundling the parsed reports with the expectation `Grid` and scenario-reference map built from the same `inputs` means a caller producing both outputs can no longer pass them out of sync with each other. Building them there also means the grid is built once per run rather than once per report section that renders it (ROCMAI-660). `PlatformReport` itself went back to `pub(crate)` once the bundle was the only thing outside callers needed. This is a deliberate encapsulation choice tighter than the full-domain-extraction convention's `pub mod x;` + `pub use x::{...};` default described above — nothing outside this crate needs the module paths themselves, only the re-exported items. Unlike [`components.rs`](../crates/e2e-report/src/components.rs), which, as noted above, keeps the module graph acyclic by depending only on [`parse.rs`](../crates/e2e-report/src/parse.rs), [`command_coverage.rs`](../crates/e2e-report/src/command_coverage.rs) and the `consolidated` module as a whole depend on each other: [`consolidated/markdown.rs`](../crates/e2e-report/src/consolidated/markdown.rs) calls `command_coverage::command_coverage_markdown`, and [`command_coverage.rs`](../crates/e2e-report/src/command_coverage.rs) consumes `consolidated::PlatformReport` (via its `commands`, `label` and `scenario_pass_map()`), which is defined in [`consolidated/mod.rs`](../crates/e2e-report/src/consolidated/mod.rs). That chain between files (`markdown.rs` to `command_coverage.rs` to `consolidated/mod.rs`) is acyclic, and no production code in `consolidated/mod.rs` depends on `command_coverage.rs` any more (only its command-coverage tests import from it); viewed as the whole `consolidated` module, though, the two still depend on each other, which moving `command_coverage.rs` under `consolidated/` would remove.

### `engines/lemonade`, `engines/vllm`, `engines/aim` — inference engine adapters

`engines/vllm` follows full domain extraction:

- [`discover_builds.rs`](../engines/vllm/src/discover_builds.rs) — the ROCm 10.x discovery table (`VLLM_ROCM_DISCOVER_BUILD_TABLE`, one row per supported `major.minor` line, with the `DiscoverVersion` series/exact constraint), the row lookup (`vllm_rocm_discover_build`) and the `major.minor` matcher it uses (`rocm_sdk_series_matches`). It is the single list of the ROCm SDK versions installed by discovery: install routing, the fail-closed static fallback and launch-time environment setup (`runtime_has_discover_build` in `runtime.rs`) all read these rows, and nothing keeps a second list in step with them. A leaf: it imports no other crate module, so `runtime.rs`, `wheel_builds.rs` and `install.rs` can all read it without importing one another's code. Its tests, including the one that pins which versions the table serves and in what order, live with it.
- [`install.rs`](../engines/vllm/src/install.rs) — ROCm/vLLM install execution: the static-pin and the ROCm 10.x discovery install routes, run through `uv`. It reads the static build table and target resolution from `wheel_builds.rs` and the discovery rows from `discover_builds.rs`, and asks `repair.rs` whether an already-resolvable environment still needs an install pass.
- [`process.rs`](../engines/vllm/src/process.rs) — the resolve-model, launch, serve and stop handlers (including engine-recipe validation and device-policy/GPU-index resolution), vLLM server spawn, launch environment and path setup, and readiness polling. The text appended to a "never became ready" failure comes from `startup_diagnostics.rs`.
- [`repair.rs`](../engines/vllm/src/repair.rs) — runtime-repair assessment: whether an already-resolvable managed vLLM environment violates vLLM's pinned dependencies and must be reinstalled (`assess_runtime_repair`, `RepairAssessment`), including the rule that treats the SDK's build of torch, and a torch the user chose with the alignment disabled, as intended rather than a defect. It imports `runtime.rs` and nothing from `install.rs`.
- [`runtime.rs`](../engines/vllm/src/runtime.rs) — TheRock/managed-runtime resolution and TheRock library/bin path derivation; the path derivation performs no filesystem writes. The launch path's compat-shim writes (a `libmpi_cxx` stub, stale-numa-shim removal) are this module's separate `ensure_therock_compat_shims`, called only from `process.rs`; the running-state payload, which never calls it, falls back to a plain directory listing instead.
- [`startup_diagnostics.rs`](../engines/vllm/src/startup_diagnostics.rs) — what a failed startup tells the user: the tail of the startup log, re-rendered line by line through `terminal::rendered_lines` (not stripped — stripping deletes line-break tokens with no separator, which welds a progress-bar repaint onto the next line), followed by the out-of-memory and engine-import-failure hints that point at `rocm diagnose`. Its single entry point is `startup_log_context`, which `process.rs` calls from `wait_for_vllm_ready`. It imports only `state.rs`, for the log-read cap.
- [`state.rs`](../engines/vllm/src/state.rs) — service state file I/O, log tailing, and health/inference probing.
- [`wheel_builds.rs`](../engines/vllm/src/wheel_builds.rs) — which vLLM wheels to install for a ROCm SDK version: the static build table (`VLLM_ROCM_BUILD_TABLE`), the install-route choice (`vllm_install_route`, which consults the discovery table in `discover_builds.rs`), target resolution including the `ROCM_CLI_VLLM_ROCM_INDEX_URL` override (`vllm_install_target`), and the static-table SDK-version matchers. It also holds `verified_torchaudio_release`, which the crate re-exports from `lib.rs` for the `rocm` binary. It imports only `discover_builds.rs` and runs no process.

[`lib.rs`](../engines/vllm/src/lib.rs) keeps only CLI/envelope dispatch and the few items shared across those modules. [`main.rs`](../engines/vllm/src/main.rs) is the `rocm-engine-vllm` binary's entry point and only calls `rocm_engine_vllm::run_cli()`.

`engines/lemonade` follows the same pattern:

- [`archive_cache.rs`](../engines/lemonade/src/archive_cache.rs) — the cached embeddable-archive layer: SHA-256 verification, verified publication of a download into the cache, and the per-archive exclusion (an in-process set plus a cross-process file lock) that `ensure_cached_archive` returns as an `ArchiveCacheGuard` for the caller to hold while it relies on the verified bytes. A leaf: it imports no other crate module. Its tests, including the two-process lock test, live with it.
- [`archive_extract.rs`](../engines/lemonade/src/archive_extract.rs) — the hardened in-process extractor for the embeddable archive (tar.gz and zip: untrusted entry names are resolved component by component, links and special entries are rejected, modes are masked) and the containment-checked `copy_tree` that moves the extracted tree into the runtime directory. A leaf: it imports no other crate module. Its extraction tests and the tar/zip property tests live with it; the property-test support (`archive_props`) is included once at the crate root so both this module and `install.rs` reach it as `crate::archive_props`.
- [`backend_alignment.rs`](../engines/lemonade/src/backend_alignment.rs) — ROCm-SDK-to-llama.cpp-backend Tier 1/Tier 2/revert alignment, including the `backend_versions.json` pin handling and the set-aside/restore of ROCm backend directories around a forced reinstall. It uses `llamacpp_backend.rs`; that module does not import it back.
- [`device_policy.rs`](../engines/lemonade/src/device_policy.rs) — device-policy and GPU-selection handling: the GPU-required policy check (a CPU-only request is refused, never downgraded), `--device`/`--gpu` argument parsing, probing and resolving the GPU ordinal(s) to pin before a launch, the device availability reported by `detect`, and the device string reported for a loaded model. A leaf: it imports no other crate module.
- [`direct_llama.rs`](../engines/lemonade/src/direct_llama.rs) — Hugging Face checkpoint/GGUF resolution and the direct-llama-server serve path (`serve_direct_llama_server`, which runs a packaged `llama-server` on a GGUF and waits for `/v1/models` to report the model). It imports `process.rs`; `process.rs` no longer imports it.
- [`footprint.rs`](../engines/lemonade/src/footprint.rs) — what an install costs on disk: the pre-install notice and free-space check.
- [`install.rs`](../engines/lemonade/src/install.rs) — embeddable-runtime download, extraction orchestration (the cache layer is in `archive_cache.rs`, the extractor in `archive_extract.rs`), and manifest persistence, plus the `LemonadeRuntime` handle and `resolve_runtime`, which wrap the persisted manifest (so `state.rs`, `process.rs` and `direct_llama.rs` reach it without importing `backend_alignment.rs`).
- [`llamacpp_backend.rs`](../engines/lemonade/src/llamacpp_backend.rs) — llama.cpp backend discovery and selection: asking `lemonade backends` what the host supports, choosing the best GPU backend (`rocm` before `vulkan`, never `cpu`), installing it with one retry, the `ROCM_LLAMACPP_BACKEND_DIRS` name list, and `find_llama_server_binary_for_backend`. It imports `direct_llama.rs` for `find_binary_in`; `direct_llama.rs` does not import it. With this module the engine's modules form no import cycle outside test code.
- [`process.rs`](../engines/lemonade/src/process.rs) — `lemond` spawn, env/path setup, readiness/health polling, and the background relaunch of the `serve-http` command (`serve_http_command_args`, `spawn_serve_http_background`). The direct `llama-server` serve loop is in `direct_llama.rs`.
- [`runtime_dir.rs`](../engines/lemonade/src/runtime_dir.rs) — `XDG_RUNTIME_DIR` tier1/2/3 hardening for the spawned child.
- [`state.rs`](../engines/lemonade/src/state.rs) — service state file I/O and port/endpoint helpers.

[`lib.rs`](../engines/lemonade/src/lib.rs) keeps only CLI/envelope dispatch and the service-lifecycle orchestration that calls across those modules. [`main.rs`](../engines/lemonade/src/main.rs) is the `rocm-engine-lemonade` binary's entry point and only calls `rocm_engine_lemonade::run_cli()`.

`engines/aim` runs models as Docker containers instead of a host process:

- [`docker.rs`](../engines/aim/src/docker.rs) — thin wrapper around the `docker` CLI binary; no `bollard`/Docker API dependency. It also owns `container_name`, the deterministic Docker-name-sanitized container identity for a service (a leaf, so both `process.rs` and `state.rs` reach it here, and `state.rs` does not need to import `process.rs`).
- [`registry.rs`](../engines/aim/src/registry.rs) — AIM image metadata (`Env`/`Labels`): read from the local daemon once the image is pulled, which works for any registry, with a best-effort Docker Hub v2 lookup as a pre-pull hint (image ref normalization, tag/digest parsing). The hint is optional; its failure never blocks a launch.
- [`process.rs`](../engines/aim/src/process.rs) — container run/readiness/stop lifecycle. `serve_http` is the process rocmd supervises: it blocks for the container's lifetime and records how it ended (`failed` and a non-zero exit for a crash or a vanished container, so recovery runs). A stale container is removed before a re-run, and a stop removes the container so its name and downloaded weights are released.
- [`state.rs`](../engines/aim/src/state.rs) — service state file I/O, including the model name the container actually serves (`served_model_id`), which differs from the image reference, and `endpoint_url`, the `/v1` base URL for a host and port. `state.rs` uses no `process.rs` item: `process.rs` imports `state.rs` and the dependency does not run the other way.
- [`install.rs`](../engines/aim/src/install.rs) — much smaller than vLLM's/Lemonade's `install.rs`: there is no venv, wheel, or runtime archive to manage, only a Docker-reachability check.

[`lib.rs`](../engines/aim/src/lib.rs) keeps only CLI/envelope dispatch (including the `builtin_*` entry points the `rocm` binary calls in-process), the detect and capabilities responses, and the few items shared across those modules. [`main.rs`](../engines/aim/src/main.rs) is the `rocm-engine-aim` binary's entry point and only calls `rocm_engine_aim::run_cli()`.
