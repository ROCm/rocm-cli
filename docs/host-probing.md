# Host probing: which stack owns each fact

Status: proposal, with the first three pairs delivered. This note changes no code and no behaviour itself, and what it proposes for a pair is decided by the change that converges that pair, which then records the decision here (the PATH lookup, pair 1, the kernel release, pair 2, and the CPU model, pair 3, have: see "PATH lookup", "Kernel version" and "CPU model"). It lists the host facts that `rocm-core` reads twice (on the hosts each is read on, see "Which host reads which fact"), says how the two reads differ, and proposes which one should survive and in what order a later series of changes could remove the other. Each pair is meant to be a separate change with its own review.

This note is a snapshot of `main` at the time of writing, not maintained documentation. It is to be retired when the convergence tickets for these pairs close, so the inventory does not keep pointing at a stale design record. Retiring it means deleting this file, removing the link to it from the host-probing bullet in the `crates/rocm-core` Boundaries of [architecture.md](architecture.md) (that bullet is the only entry it has; it is not a table row), and rewording the comments in `rocm-core` that cite it by name ([`probe_exec.rs`](../crates/rocm-core/src/probe_exec.rs), [`host_gpu/os_facts.rs`](../crates/rocm-core/src/host_gpu/os_facts.rs), [`examine/host_env.rs`](../crates/rocm-core/src/examine/host_env.rs) and [`examine/wsl.rs`](../crates/rocm-core/src/examine/wsl.rs)).

How to read the claims below. Everything marked "verified" was read in the source on `main` at the time of writing, and the symbols named are the identity if a file moves. Nothing was executed on a Windows host. The one run on a WSL host is a single `rocm examine --json` with a local debug build of unrecorded revision, noted under "CPU model", and every count of runs or queries below comes from reading the call graph, not from measuring a process. Anything that depends on how a real machine behaves, rather than on what the code says, is marked UNCONFIRMED.

## The two stacks

| | Summary stack | Examination stack |
|---|---|---|
| Entry point | `ExamineSummary::gather` in [host_gpu.rs](../crates/rocm-core/src/host_gpu.rs) | `Examination::probe` in [examine.rs](../crates/rocm-core/src/examine.rs) |
| Printed by | the text of `rocm examine`, the `summary` object of `rocm examine --json`, the MCP and bridge snapshots, `rocm install driver` | the top level of `rocm examine --json`, `rocm diagnose`, Doctor reports, remote probes |
| Subprocess helper | `capture_optional_command*` in [capture.rs](../crates/rocm-core/src/host_gpu/capture.rs) | `run` and `which` in [probe_exec.rs](../crates/rocm-core/src/probe_exec.rs) |
| A probe that fails | reads as `None`, no trace (an opt-in stderr line with `ROCM_CLI_DEBUG_COMMAND_CAPTURE`) | usually a `probe_failures` entry, which also degrades `status` |

The two meet in one command. [examine_cmd.rs](../apps/rocm/src/examine_cmd.rs) builds the `--json` document by running `Examination::probe_with_interpreter` and then `ExamineSummary::gather`, so a fact below appears twice in one document, read by two separate runs, only on the hosts where both stacks read it ("Which host reads which fact" lists them, including the two cases that are not "twice": the CPU on WSL and `kernel_release` on Windows). The text form ([examine_report_text.rs](../apps/rocm/src/examine_report_text.rs)) prints the summary only, and `rocm diagnose` ([diagnose_cmd.rs](../apps/rocm/src/diagnose_cmd.rs)) reasons over the examination only. The existing scenarios `examine-machine-readable-report` and `examine-both-forms-agree-on-gpu` in [examine.feature](../tests/e2e-cucumber/features/examine.feature) hold the two forms level on GPU presence and on the facts the text states; none of them compares kernel, CPU or the gfx target of an individual adapter.

The direction of the import is already one-way, but sharing an implementation is not the same as sharing an observation, and the note keeps the two apart. Verified, in production code: the examination stack calls into the summary stack for `is_wsl_host` (`probe_os`, `probe_wsl`), `detect_wsl_summary` and `ldconfig_lists_librocdxg` (both in `probe_wsl`), `ldconfig_cache` (`probe_comgr` in [library_copies.rs](../crates/rocm-core/src/examine/library_copies.rs)), `detect_windows_amd_driver_info` (`probe_adrenalin_windows`) and `gfx_target_from_pnp_device_id` (`parse_gpus_windows_output`; the function lives in [gfx_target.rs](../crates/rocm-core/src/gfx_target.rs) and is re-exported through `host_gpu`). `detect_distro_name` is not on that list: the only references to it under `examine/` are two tests in [host_env.rs](../crates/rocm-core/src/examine/host_env.rs). In production `record_distro` calls `hardware_root::read_os_release` and `os_release::parse` directly, which is the reader and parser `detect_distro_name` is built on, so the two share an implementation and still read the file separately. Nothing under `host_gpu/` imports `examine` outside the summary module's own tests and doc comments.

Which of these is also one read is a separate question, and for most of them the answer is no. `rocm examine --json` runs `detect_wsl_summary` twice on WSL, once in `ExamineSummary::gather` and once in `probe_wsl`, and each run repeats the device-node and ROCm file checks, one `ldconfig -p` and the two `PATH` lookups; `probe_wsl` then asks `ldconfig` a third time through `ldconfig_lists_librocdxg`, and `probe_comgr` a fourth through `ldconfig_cache`. `is_wsl_host` re-reads `/dev/dxg` and `/proc/version` at every call. The os-release file is read once by each stack, and the Windows driver is read by its own inventory run (see "Windows GPU query"). So the WSL check, the os-release parser, the Windows driver and the `ldconfig` lookup are shared code, not yet shared results: none of them is a duplicate read that has already been removed, and the plan below does not count them as done. The proposals continue in the same import direction, so the rule of thumb is: the summary stack owns how a fact is asked of the operating system, the examination stack owns the document (field names, `probe_failures`, the JSON contract) and calls down. Whether the two stacks should also share the answer within one run, rather than ask twice through the same code, is left open at the end.

## Which host reads which fact

Every pair below is read on a subset of the hosts, and the subset decides which characterisation test and which scenario can exist. This table is derived from the branches of `Examination::probe_with_interpreter` (the WSL branch returns early, before the native Linux and Windows branches), `probe_os` and `probe_wsl_distro_from_host`, all in [examine.rs](../crates/rocm-core/src/examine.rs), [host_env.rs](../crates/rocm-core/src/examine/host_env.rs) and [wsl.rs](../crates/rocm-core/src/examine/wsl.rs), and from `ExamineSummary::gather` in [host_gpu.rs](../crates/rocm-core/src/host_gpu.rs). "Both" means both stacks read it in one `rocm examine --json` run.

| Fact | Native Linux | WSL (probing inside the distro) | Native Windows | Windows host inspecting a WSL distro (`probe_wsl_distro_from_host`) |
|---|---|---|---|---|
| Kernel version | both, through `detect_kernel_version` (before the change each ran `uname -r` itself) | both: `probe_os` runs before the WSL branch returns | summary `kernel` from `cmd /C ver`; `kernel_release` stays empty | examination only, from `uname -r` run inside the distro by a shell script (`WSL_REMOTE_PROBE`), a third implementation |
| CPU model and vendor | both, through one reader | summary only: the examination returns before `probe_cpu_linux`, so `cpu_model` is empty and `cpu_vendor` is `unknown` (unchanged by the CPU-model change, option (a)) | both, each running the system inventory's query, the examination through the reader and the summary through the inventory it holds | neither: `cpu_model` empty |
| Windows adapter list | not applicable | examination `gpus[]` stays empty (the WSL branch skips the GPU probes); the summary asks the Windows host for the display target only | both | not collected here; the host driver is read through the summary's inventory (`detect_local_windows_host_driver`) |
| Marketing name to gfx target | examination only (the `lspci` scan); the summary reads sysfs and KFD, not names | summary only, through the Windows host's display name | both | not collected |
| PATH lookup | `which` | `which`, asked by both stacks for `rocminfo` (before the change the summary asked `tool_on_path`, a second copy) | `which` | `which` for `wsl.exe` only |
| Subprocess runners (which helpers exist on the host) | three: `capture_optional_command*`, `run`, `run_with_timeout` (`capture_diagnostic_command` is Windows only) | the same three | all four | `run` and `run_utf16le` (both over `run_raw`), plus the summary's capture helper through the inventory behind `detect_local_windows_host_driver` |

A pair that one host reads with only one stack cannot disagree on that host, but it can still change when a shared helper is changed, so the characterisation tests below name the hosts they cover and say so where a row is empty.

## Kernel version

Verdict: confirmed duplicate for `uname -r`, now converged (see "Decided and delivered" below). `uname -v` in `probe_os` has no twin. The comparison that follows is how the two copies differed before that change, kept as the record of what it moved.

| | Summary | Examination |
|---|---|---|
| Symbol | `detect_kernel_version` in [os_facts.rs](../crates/rocm-core/src/host_gpu/os_facts.rs) | `probe_os` in [host_env.rs](../crates/rocm-core/src/examine/host_env.rs) |
| Linux command | `uname -r`, 1.5 s | `uname -r`, 5 s (`SHORT`) |
| Non-zero exit | `None`, stdout dropped | exit code ignored, stdout kept |
| Failure | `None`, reads `<unknown>` | empty `kernel_release`, no `probe_failures` entry |
| Output decoding | strict UTF-8, else `None` | lossy |
| Windows | `cmd /C ver` as `kernel`, resolved through the System32 candidate | the same command as `os_version`; `kernel_release` stays empty |
| Field | `kernel:` in the text, `summary.kernel` in JSON | `kernel_release` (and `os_version` from `uname -v`) |

What a user can see: on a native Linux or WSL host where `uname` is slow or fails, `kernel:` can read `<unknown>` while `kernel_release` is filled in, or the reverse. UNCONFIRMED on a real host; the code allows it. `kernel_release` also feeds `is_wsl1_kernel` for the WSL facts, so its empty-versus-populated behaviour is not cosmetic.

Proposal: `detect_kernel_version` survives and `probe_os` calls it for `kernel_release` on Linux, keeping `uname -v` where it is. Calling it on Windows too would populate `kernel_release` there, which is a visible change to the JSON; decide that separately. The timeout is open (1.5 s or 5 s): the characterisation test should pin both before one is chosen. Hosts the test covers: native Linux and WSL (one code path, since `probe_os` runs before the WSL branch returns), with a fake `uname` that succeeds, exits non-zero with stdout, times out, and prints nothing; plus a WSL 1 style and a WSL 2 style string through `probe_wsl`, because `is_wsl1_kernel` reads the field. Windows is covered only by a unit test behind an injectable runner, which pins that `kernel_release` stays empty unless that change is decided. The distro probe's shell `uname -r` has no twin to compare and is out of this pair.

### Decided and delivered

The change took the proposed survivor: `detect_kernel_version` in [os_facts.rs](../crates/rocm-core/src/host_gpu/os_facts.rs) is the one `uname -r` reader, and `probe_os` in [host_env.rs](../crates/rocm-core/src/examine/host_env.rs) calls it for `kernel_release` on Linux, native and WSL alike, with a failed read left empty. It is also one read per inspection where one command runs both stacks: `rocm examine --json` builds both through `Examination::probe_with_summary`, which probes this host and gathers the summary from that examination with the crate-private `ExamineSummary::gather_after` (so no caller can pair the summary with an examination of another host, such as one deserialised from a report), and the summary takes the examination's `kernel_release` (a failed read included) on Linux instead of running `uname -r` again, so the two fields cannot disagree on a transient failure and a hung `uname` costs one timeout, not two. Callers that gather only the summary still read for themselves, and most of them read once per call: the text form of `rocm examine` (`examine_human_report` in [examine_report_text.rs](../apps/rocm/src/examine_report_text.rs)), the in-process `rocm examine` of the chat bridge, the bridge snapshots and the host snapshot, the sandbox examine snapshot of `rocmd`, the free-form answer, `rocm install driver --reconcile`, and the runtime-install finalizer (which asks only when a runtime that cannot serve raises the question of whether the host has a GPU).

Three paths read more than once for one user action, as they did before this change:

- the `examine` and `doctor` tools of the chat bridge in [mcp_bridge.rs](../apps/rocm/src/chat/mcp_bridge.rs) gather the summary and then render the text form, which gathers it again (two reads in one process);
- the `examine` tool of `rocmd` in [mcp.rs](../apps/rocmd/src/mcp.rs) gathers the summary in process and then runs `rocm examine` as a child process, whose text form gathers it again (two reads, in two processes);
- `rocm install driver` in [driver_install.rs](../apps/rocm/src/driver_install.rs) gathers the summary before it builds the plan and, when it runs the plan, once more afterwards (one read for a dry run or a plan that is only reported, two for an executed install).

`uname -v` stays in `probe_os`. Windows is out of this change: the examination still leaves `kernel_release` empty there and the summary still reads `cmd /C ver` under the shorter optional-command timeout; whether `kernel_release` should be filled on Windows stays open, and so does the Windows unit test the proposal mentioned, because the Windows branches did not change.

The four open questions are decided as follows.

- Timeout: 5 s, the longer of the two old limits (`KERNEL_RELEASE_TIMEOUT`, written out as five seconds rather than borrowed from `SHORT`, which is also 5 s today, and pinned by `the_kernel_release_timeout_is_five_seconds`). `uname -r` is a few bytes the kernel hands over, so a read that takes seconds is a stalled host, where waiting costs little and a spurious "unknown" costs more: `kernel_release` feeds the WSL version check and the kernel-dependent diagnoses, which read an empty value as nothing to report. The cost is that every caller of `ExamineSummary::gather` and `gather_without_driver_facts` that reads the kernel for itself on Linux, native or WSL (the text of `rocm examine`, the MCP and bridge snapshots, the free-form answer, `rocm install driver` and its `--reconcile` form, the runtime-install finalizer, and `rocmd`'s host snapshot, MCP and sandbox paths) can wait up to 5 s per read instead of 1.5 s on a host whose `uname` hangs, and a caller that reads more than once pays that more than once: the two reads of each of the three multi-read paths listed above run one after the other, so each of those can wait up to 10 s instead of 3 s. None of these is on a path run for every command. `rocm examine --json` waits for one timeout, because it hands the examination's read to the summary. Windows does not change: the summary there reads `cmd /C ver` under the 1.5 s limit, and the examination-only callers, such as `rocm diagnose`, already waited up to 5 s in `probe_os`.
- Failure: `None` in the summary (`<unknown>` in the text, null in the JSON) and an empty `kernel_release` in the examination, with no `probe_failures` entry, as before. Adding an entry would change `status` to degraded on a host without a usable `uname`, such as a minimal container, which is a bigger change than the pair warrants. An empty `kernel_release` reads as WSL 2 in `is_wsl1_kernel`, as before.
- Non-zero exit with output: dropped by both. The examination used to keep what a failing `uname` printed; the summary dropped it. A release from a `uname` that failed is not trustworthy.
- Decoding: strict UTF-8 for both. The examination used to decode lossily. A release is ASCII in practice, so the only input that moves is one that is not UTF-8 at all, and a string with replacement characters in it would reach the diagnoses and the WSL check as if it were a release.

The answers that moved, each with the test that pins it:

| Difference | Before | Now | Pinned by |
|---|---|---|---|
| `uname` prints a release and exits non-zero | summary: none; examination: the release | none in both | `a_non_zero_exit_with_output_is_dropped_by_both`, scenario `examine-44` |
| `uname` output that is not UTF-8 | summary: none; examination: the release with the bad byte replaced | none in both | `output_that_is_not_utf8_is_dropped_by_both` |
| `uname` that answers after 2 s | summary: none (1.5 s); examination: the release (5 s) | the release in both | `an_answer_after_two_seconds_is_read_by_both` |
| `uname` that never answers | none in both | none in both; the unit test's child reads twice, each bounded by the one 5 s limit | `a_uname_that_never_answers_reads_as_nothing_in_both_within_the_timeout` (it checks the elapsed time, since the answers alone cannot tell a timeout from none) |
| `uname` that prints nothing | none in both | unchanged | `a_silent_uname_reads_as_nothing_in_both` |
| WSL 1 and WSL 2 style releases | read as printed by both | unchanged; `probe_wsl` makes version 1 of the first and version 2 of the second, of an empty one and of the original `-microsoft-standard` form | `both_read_wsl_style_releases_as_printed`, `probe_wsl_reads_the_wsl_version_from_the_kernel_release` |
| A failed read and `probe_failures` | no entry | no entry | the check in the same tests that no case leaves a `probe_failures` entry about the kernel, and scenario `examine-44` |
| Reads in one `rocm examine --json` run | two (`probe_os` and the summary each ran `uname -r`) | one: the summary takes the examination's | `the_summary_reads_the_kernel_only_when_the_examination_did_not` (a counted read), and the last step of scenario `examine-43`, which counts the calls of a stand-in `uname` |

The scenarios `examine-43` and `examine-44` in [examine.feature](../tests/e2e-cucumber/features/examine.feature) drive the observable answer on the Linux lane, native and WSL: with a stand-in `uname` first on `PATH`, one `rocm examine --json` run holds `summary.kernel` and `kernel_release` level on a specific release and shows from the stand-in's call log that `uname -r` ran once, and, for a `uname` that prints a release and then fails, holds both empty with no kernel `probe_failures` entry. The unit tests plant the same stand-in in a child copy of the test binary with its own `PATH`, because a test thread cannot change `PATH` without disturbing every other test.

## CPU model

Verdict: confirmed duplicate on native Linux and Windows, and on Windows three implementations, now converged (see "Decided and delivered" below); the comparison that follows is how the copies differed before that change, kept as the record of what it moved. On WSL it is not a duplicate: only the summary reads the CPU there (see the table above and the paragraph on WSL below). The three Windows implementations are `detect_cpu_model` (its own PowerShell call), the `CPU` row of `WINDOWS_SYSTEM_INVENTORY_SCRIPT` in [windows_inventory.rs](../crates/rocm-core/src/host_gpu/windows_inventory.rs), and `probe_cpu_windows`. They are not three reads of one run in the usual case: the summary reads the inventory row first and calls `detect_cpu_model` only when no inventory exists, so a host whose inventory answers is read twice in `rocm examine --json` and one whose inventory does not answer is read three times (derived from `detect_cpu_model_with_windows_inventory` in [host_gpu.rs](../crates/rocm-core/src/host_gpu.rs); UNCONFIRMED on a live host).

| | Summary | Examination |
|---|---|---|
| Symbols | `detect_cpu_model` and `normalize_cpu_model` in [os_facts.rs](../crates/rocm-core/src/host_gpu/os_facts.rs) | `probe_cpu_linux`, `probe_cpu_windows` in [host_env.rs](../crates/rocm-core/src/examine/host_env.rs) |
| Linux source | `/proc/cpuinfo`: the first line that is `model name` or `Hardware` | `/proc/cpuinfo`: `model name` only, plus `vendor_id` |
| Whitespace | collapsed | trimmed only |
| Windows | `Win32_Processor` name, 1.5 s | same class, 8 s, first line only |
| Vendor | not recorded | `cpu_vendor`: from `vendor_id` on Linux, from the model string (`amd` or `intel`) on Windows |
| Failure | `<unknown>` | Windows: a `probe_failures` entry; Linux: empty model, vendor `unknown` |

What a user can see on WSL: the text and `summary.cpu` show the CPU, while `cpu_model` is empty and `cpu_vendor` is `unknown` in the JSON, on every WSL host and not only on odd ones. The cause is structural: `Examination::probe_with_interpreter` runs `probe_os`, sees `is_wsl`, and returns from its WSL branch before the native Linux branch reaches `probe_cpu_linux`, and `probe_wsl` sets no CPU field. One `rocm examine --json` run on a WSL2 host with a local debug build of unrecorded revision showed exactly that (`is_wsl` true, `cpu_model` empty, `cpu_vendor` `unknown`, `summary.cpu` populated); that is one host, so other WSL hosts are UNCONFIRMED, though the branch has no condition that would make them differ.

What a user can see on native Linux and Windows: a board whose cpuinfo has `Hardware` but no `model name` shows a CPU in the text and an empty `cpu_model` with vendor `unknown` in the JSON. A model string with repeated spaces inside it differs between the two forms (UNCONFIRMED which real CPUs report one; the code path differs). A Windows host where the 1.5 s query times out shows `cpu: <unknown>` beside a populated `cpu_model` (UNCONFIRMED, timing). No diagnosis checker reads `cpu_model` or `cpu_vendor` today (verified by grep); they reach Doctor reports and the JSON only.

Proposal: one reader in `os_facts` that returns the model and the vendor together (Linux from cpuinfo with the `Hardware` fallback and `vendor_id`; Windows from the inventory row, deriving the vendor from the model as `probe_cpu_windows` does). `probe_cpu_linux` and `probe_cpu_windows` call it. The open question here, whether the whitespace collapse should reach `cpu_model` in Doctor reports, is decided under "Decided and delivered".

This change does not reach WSL. The early return stays, so on WSL `cpu_model` stays empty and a comparison of `summary.cpu` with `cpu_model` fails there before and after. There are two ways to handle that, and the change has to pick one and say so in its PR text. Either (a) the comparison, in the characterisation test and in the scenario, is scoped to hosts where `is_wsl` is false, and the empty WSL fields are pinned as an existing difference; or (b) collecting CPU facts on WSL becomes an explicit behaviour change: the WSL branch calls the reader too, `cpu_model` and `cpu_vendor` appear in the WSL JSON and in Doctor reports, and the Windows-hosted distro probe needs its own answer (its `WSL_REMOTE_PROBE` shell script would have to print the CPU, since the reader runs on the host, not in the distro). The note recommends (a) for the convergence change and (b), if wanted, as its own change, because (b) adds a populated field to a document that consumers read today as empty. Hosts the characterisation test covers: native Linux from a fixture `/proc/cpuinfo` through `host_path` (`model name` present, `Hardware` only, repeated spaces, no `vendor_id`), WSL (a simulated host root, pinning the summary populated and the examination empty), and Windows through an injectable runner (inventory row present, absent, query failing, query timing out, empty output).

### Decided and delivered

The change took the survivor proposed above. `CpuFacts` in [os_facts.rs](../crates/rocm-core/src/host_gpu/os_facts.rs) carries the model, or none, and the vendor, and one reader per platform fills it: on Linux `read_linux_cpu_facts` reads `/proc/cpuinfo` through `host_path` and `cpu_facts_from_cpuinfo` takes the first `model name` or `Hardware` line with a value and the first `vendor_id` with a value, and on Windows `windows_cpu_facts_with` runs the CPU-and-RAM query of the system inventory (`windows_system_inventory_with` in [windows_inventory.rs](../crates/rocm-core/src/host_gpu/windows_inventory.rs)) and `cpu_facts_from_windows_inventory` takes its CPU row, deriving the vendor from the model string (`amd` or `intel`, else `unknown`) as `probe_cpu_windows` did. `probe_cpu_linux` and `probe_cpu_windows` fill `cpu_model` and `cpu_vendor` from them, and the summary reads the same facts: `detect_cpu_model` is the Linux model and answers `None` off Linux, so it cannot start a Windows query, and on Windows the summary reads the CPU row of the inventory it already holds (`summary_cpu` in [host_gpu.rs](../crates/rocm-core/src/host_gpu.rs)), which is the same row through the same function. Both PowerShell `Win32_Processor` queries that were separate from the inventory are gone, and so is the Windows arm `detect_cpu_model` had in the first version of this change: nothing reached it in production, and it was exactly the path that would have brought the second query back. The injectable query (`windows_cpu_facts_with`, and `windows_system_inventory_with` under it) is what runs the Windows logic in a unit test on the Linux and Windows jobs.

WSL is option (a): the early return stays, so on WSL `cpu_model` is empty and `cpu_vendor` is `unknown` while the summary shows the CPU, exactly as before. The comparison of `summary.cpu` with `cpu_model` in the scenarios is scoped to hosts where `is_wsl` is false, and the empty WSL fields are pinned as an existing difference by `on_wsl_the_summary_reads_the_cpu_and_the_examination_does_not` and scenario `examine-47`, so collecting CPU facts on WSL (option (b)) is a visible change of its own, which turns both.

The open questions are decided as follows.

- Whitespace: the collapse reaches `cpu_model`, so the model is one string in both forms. Nothing diagnoses from `cpu_model` or `cpu_vendor` (grep of the crates), so the only places that see the change are the JSON and the Doctor reports; a consumer that matched the old padded spelling is the one that sees it.
- The `Hardware`-only case: the `Hardware` value is the model and the vendor stays `unknown`, because such a file names none. The model is the first line of either kind, as the summary always had it, so with `Hardware` before `model name` the examination now reads the `Hardware` value where it read the `model name`; real cpuinfo prints `Hardware` after the per-core blocks, so that order is a fixture, not a host this note knows of.
- Empty versus unknown: a CPU that could not be read is no model (shown `<unknown>` in the text, `null` in `summary.cpu`) in the summary and an empty `cpu_model` with `cpu_vendor` `unknown` in the examination, as before, and a vendor line with no value names no vendor. On Linux that is not a `probe_failures` entry, as before. On Windows the examination still records a `probe_failures` entry, now worded for the query that runs (`The Windows system inventory query (CPU and RAM) reported no CPU; cannot identify CPU.`, where it named a `Win32_Processor` query that no longer runs), now for any read that gives no CPU (a query that failed, timed out, printed nothing or printed no CPU row), where it recorded it for a non-zero exit or blank output.
- The Windows timeout: one limit of 5 s, the inventory's own for every other query, for the one query both stacks run. The summary's system query was 1.5 s (and its own CPU query too) and the examination's was 8 s, so the summary now waits longer, for its RAM row as well, and the examination gives up 3 s sooner. The reason is that the examination runs the query first in a `--json` run, on a PowerShell that has not started yet, where 1.5 s may not be enough and a spurious empty `cpu_model` with a `probe_failures` entry costs more than waiting; 8 s was not taken for the shared query because it would also be the worst case of every startup path that gathers the summary on a host whose PowerShell hangs. Neither number was measured: UNCONFIRMED on a real Windows host.
- Queries per run: on native Windows `rocm examine --json` runs the system query twice now (down from two or three): once in the summary's `assemble_windows_inventory` and once in `probe_cpu_windows`. They are not shared within a run because the examination is built first and the summary after it, by separate calls in `examine_cmd.rs` that pass nothing between them, and sharing the answer means choosing which stack owns it, which is the open question below about one run sharing answers between the stacks. This change removes the third read and the second implementation; it does not claim one query.
- The inventory fallback: dropped. With no inventory at all, `detect_cpu_model` used to run a `Win32_Processor` query of its own, but an absent inventory means every source, the system query included, had just failed, so the second try repeated a failed query. The summary now shows `<unknown>` there. Keeping it would have meant keeping a second Windows implementation, which is what this change removes. The summary's RAM keeps its own fallback query (`detect_system_ram_gib_with_windows_inventory`), and that is deliberate here and not an oversight: `detect_system_ram_gib` is a public reader that `model_fit` calls with no inventory at all, so its Windows query has to exist, and changing what the summary shows for RAM when the inventory is absent is a behaviour change for a fact this change does not touch. Dropping that fallback so RAM follows the CPU is a follow-up, with its own scenario or unit test.

The differences that moved, each with the test that pins it (the unit tests are in `os_facts.rs`, `host_gpu.rs` and `host_env.rs`; the scenarios are in `examine.feature`):

Keeping the call sites unchanged does not keep their answers unchanged: the differences listed above become the intended observable differences of this change (see the first item of the order below). The empty-entry case is a real choice, because either answer changes one side. Following `PATH` semantics matches what a shell or `execvp` does with an empty entry, and makes `which` read a file in the current directory as found, which widens what the examination calls installed (fifteen or so capability checks, including `sudo` and `usermod`). Skipping empty entries keeps the examination's answer and changes only the summary's on WSL, at the cost of disagreeing with `execvp` for a program the CLI later starts by bare name. The note does not pick one; the change has to, and its PR text states which.

### Decided and delivered

The change took the survivor proposed above: `which` in [probe_exec.rs](../crates/rocm-core/src/probe_exec.rs) has the behaviour `tool_on_path` had, `tool_path_candidates` moved there with it (the capture runner in [capture.rs](../crates/rocm-core/src/host_gpu/capture.rs) and the Windows diagnostics capture import it from there), `detect_wsl_summary` asks `which` for `rocminfo` and `cargo`, and `tool_on_path` is gone. The Windows spellings are computed by `path_candidates`, which takes the platform, `PATHEXT` and the system root as arguments, and the search by `found_in`, which takes the directories and an existence test, so both are unit-tested on every host.

The empty-entry question is decided as skip. An empty `PATH` entry is not read as the current directory. That keeps the examination's answer, which is what fifteen or so capability checks (including `sudo` and `usermod`) already relied on, so the only answer the empty-entry rule moves is the summary's on WSL, where a `rocminfo` or `cargo` file in the current directory no longer reads as installed. It also settles the Windows question the note could not answer: how `std::env::split_paths` treats an empty entry there no longer matters, because the entry is dropped either way. The cost is the one named above: a program the CLI later starts by bare name can still resolve from the current directory through the operating system when `PATH` has an empty entry, and the lookup, which does not start anything, no longer agrees with that. Guarding the runners against that (`capture_optional_command*` and `run` start a bare name through `Command`, so the operating system resolves an empty entry for them) is a property of how they spawn, not of the lookup, so it belongs to the subprocess-runners pair (item 6 below) and is not changed here.

## Subprocess runners

Verdict: confirmed duplicate, and a family rather than a pair.

| Helper | Streams | Result | Default timeout | Reader threads |
|---|---|---|---|---|
| `capture_optional_command_with_timeout` ([capture.rs](../crates/rocm-core/src/host_gpu/capture.rs)) | stdout only; stderr discarded | `Option<String>`: only on success and valid UTF-8 | 1.5 s, 5 s for inventory queries | joined with no limit; tries each candidate spelling in turn after a spawn failure, a non-zero exit or a timeout |
| `run`, `run_raw` ([probe_exec.rs](../crates/rocm-core/src/probe_exec.rs)) | both | `(rc, stdout, stderr)`, `127` for spawn failure, `124` for timeout, lossy UTF-8 | 5 s, 8 s, 15 s | joined with no limit |
| `capture_diagnostic_command` ([diagnostics.rs](../crates/rocm-core/src/host_gpu/diagnostics.rs), Windows only) | both | status, text, error and a timed-out flag | per call | joined with no limit |
| `run_with_timeout` ([process.rs](../crates/rocm-core/src/process.rs)) | both | `Result<Output>`; a timeout is an `Err` that quotes bounded output | per call | abandoned after a short grace |

The first three join their reader threads with no limit, so a grandchild that keeps the pipe open can outlast their timeout; [process.rs](../crates/rocm-core/src/process.rs) documents why `run_with_timeout` does not. That defect is already tracked in [#623](https://github.com/ROCm/rocm-cli/issues/623), which lists the same helpers. Separately, the candidate loop in `capture_optional_command_with_timeout` keeps going after any failure of a candidate, a timeout included, so on Windows a hung `powershell` may be started again under several spellings (UNCONFIRMED; the loop does not stop on a timeout). `capture_diagnostic_command` moves to the next candidate only when a spawn fails.

The helpers differ on a successful run too, not only on a timeout. Each of these is derived from the code and not run:

- Late descendant output. After the child exits, `run_with_timeout` (`run_captured` in [process.rs](../crates/rocm-core/src/process.rs)) gives the readers `DRAIN_GRACE` (200 ms) and then takes the buffer and abandons them, so a descendant that writes later than that after the child exited successfully contributes nothing. `run_raw`, `capture_optional_command_candidate_with_timeout` and `capture_diagnostic_command` join the readers and so wait for EOF, keeping whatever the descendant writes however late, and waiting without a bound if it never closes the pipe. Output the child itself wrote before exiting is kept by both. The existing tests `output_arriving_after_the_child_exits_is_still_collected` and `a_grandchild_holding_the_pipe_does_not_hold_a_successful_call` in [process.rs](../crates/rocm-core/src/process.rs) cover `run_with_timeout` only, and the first uses a 0.1 s delay inside the grace, so neither shows the difference.
- A read error on a pipe. The three older helpers discard it (`let _ = read_to_end`) and keep the bytes read so far with the real exit status; `run_with_timeout` turns a read failure on a run that did not time out into an error and drops the bytes.
- A failure to wait. `run_raw` treats a `try_wait` error as `124` without killing the child and then joins the readers; `capture_optional_command_candidate_with_timeout` and `run_with_timeout` kill it first.
- Spawn failure and encoding. `run` reports `127` with empty output where `run_with_timeout` returns an `Err` (a spawn failure there is an `std::io::Error` under a context message); `capture_optional_command*` returns `None` for output that is not UTF-8 where `run` keeps it lossily, and discards stderr where the others capture it, so after the change a descendant that holds only stderr open costs it up to the 200 ms grace, where it cost nothing before.
- Timing. The poll interval is 20 ms in `run_raw`, 25 ms in the two capture loops under `host_gpu/` and 50 ms in `run_with_timeout`, so an exit is noticed up to about 30 ms later.

The capture type from the earlier `rocm` capture work is on `main`: `CommandCapture` in [command_capture.rs](../crates/rocm-core/src/command_capture.rs), built over `run_with_timeout`. As it stands it is not enough for the probes, and the reasons are specific. Its constructor runs the `rocm` binary only (the general `capture_program` is not public). It stores lossy text, so `run_utf16le`, which decodes `wsl.exe`'s UTF-16LE output from raw bytes, cannot use it. It reports `1` for a child killed by a signal, which is also a real exit code. And `run_with_timeout` signals a timeout only through the text of its error, while a spawn failure should be recognisable by downcasting to `std::io::Error` (not exercised here), so a probe cannot tell "not installed" (quiet) from "timed out" (worth a `probe_failures` entry) without parsing a message.

Proposal: `run_with_timeout` survives as the one bounded executor, with `CommandCapture` as the shared result carrier extended with a typed outcome (not found, timed out, exited with a code) rather than a second capture type. `run` and `capture_optional_command*` become thin adapters that keep their current return shapes, so the first change touches no call site. That is not the same as keeping every observable result: the timeout path and the successful-run differences listed above are where they differ (see the last item of the order below). Keeping the strict-UTF-8 and lossy decodings, and the partial output after a timeout that `run` returns, needs the raw bytes from the executor, which is a second reason the carrier has to hold bytes rather than lossy text. The adapters can then be retired site by site as the pairs above remove call sites. This pair overlaps [#623](https://github.com/ROCm/rocm-cli/issues/623); extend that issue's scope with the typed outcome rather than opening a parallel one.

## Proposed order

One pair per change. Each begins with a commit that adds a characterisation test and is green against the code as it is: it pins what both copies return for the same input, and where they differ it pins each copy's answer, with a comment naming the pair. The convergence commit then flips the assertions that are meant to change and the PR text lists each one as a user-visible difference. Tests that need a program on `PATH` use the fake-executable helper in [fake_executable.rs](../crates/rocm-core/src/fake_executable.rs); Windows-only logic goes behind an injectable function so a unit test runs on the Windows job, as the inventory already does with `WindowsInventorySources`.

1. PATH lookup (delivered: see "Decided and delivered" under "PATH lookup"). Smallest, and it settles where `tool_path_candidates` lives before the runner work needs it. It is not output-preserving: the differences listed under "PATH lookup" change which tools are reported as present, and its PR text lists each one as intentional, with the characterisation test that pins it. Hosts covered: Linux, which is also WSL's code path, for the empty entry, the non-UTF-8 `PATH` (set through an `OsString` environment value) and the current-directory file; Windows through an injectable resolver for the `PATHEXT` spellings, the System32 candidates and the `;` splitting, since the Linux lane cannot run them.
2. Kernel version (delivered: see "Decided and delivered" under "Kernel version"). A single command; it settled the timeout and the empty-versus-`None` question. Hosts covered as set out under "Kernel version".
3. CPU model (delivered: see "Decided and delivered" under "CPU model"). Adds the model-and-vendor reader; needs the Windows inventory row, which already exists. Its PR says which WSL option under "CPU model" it takes, (a) or (b); a PR that does not is not ready. It took (a). Not output-preserving: the differences listed under "CPU model" change a model's spelling, a `Hardware`-only board's `cpu_model`, and the time the Windows reads wait.
4. Marketing name to gfx target, by finishing [#521](https://github.com/ROCm/rocm-cli/pull/521). It must land before the next item, so that `gpus[]` is not rebuilt on top of two name tables.
5. Windows GPU query. The riskiest: it needs an answer on NVIDIA and on adapter names, and a Windows lane. Scenario `examine-windows-driver-version-date-and-age` already runs there; a new scenario should compare the text's `detected_gfx_target` with the JSON `gpus[]` on a named adapter. Native Windows only; no scenario can run this on the Linux or WSL lanes.
6. Subprocess runners. Last, because items 1 to 5 reduce the number of call sites, but independent: the bounded-join fix in [#623](https://github.com/ROCm/rocm-cli/issues/623) does not wait for it and can land at any time. It has two intended differences, and the second is easy to miss because it needs no timeout: a probe behind a hung grandchild returns at its deadline instead of late (with possibly different output kept after a timeout), and a successful capture can keep less, because a descendant that writes more than `DRAIN_GRACE` (200 ms) after the child exited loses that later output where the older helpers waited for EOF. Each of the other successful-run differences listed under "Subprocess runners" needs its own line in the PR text. The characterisation test for this item comes first and must include late descendant output: a child that prints `early`, exits 0 and leaves a descendant that prints `late` after about 0.5 s, run through each of `run` (over `run_raw`, which `run_utf16le` shares), `capture_optional_command*` and `run_with_timeout`, pinning that the first two return both lines and `run_with_timeout` only `early`. Hosts covered: Linux and WSL with shell fixtures (the same shape the `process.rs` tests already use for the grace); `capture_diagnostic_command` and the Windows spellings are Windows only, so on the Windows job they get the injectable-function test of the adapter's result translation instead. UNCONFIRMED whether a Windows child can be arranged to leave a late-writing descendant in the test harness; if not, the PR says that path is untested and why.

Items 2 and 3 should add a scenario (item 3 did: `examine-45` to `examine-47`) that compares `summary.kernel` with `kernel_release` and `summary.cpu` with `cpu_model` in one `--json` run, since no existing scenario does. Each comparison is scoped to the hosts where both sides are filled: kernel on native Linux and WSL, CPU on native Linux and Windows (option (a) under "CPU model"). The Linux lane can also drive a WSL variant with a simulated host root (`ROCM_CLI_TEST_HOST_ROOT` in an `e2e-test-hooks` build, with a `/dev/dxg`, a `/proc/version` that reads as WSL and a `/proc/cpuinfo`, as [hardware_root.rs](../crates/rocm-core/src/hardware_root.rs) describes), which pins the empty WSL CPU fields; `uname` still runs for real there, so a kernel value is compared rather than fixed. Assert the specific values, not only that both are non-empty.

No item is output-preserving without qualification, and the PR for each says which of its differences are intended instead of claiming nothing changed. Items 2 to 5 change visible output (a kernel or CPU string, a gfx target, an adapter name or vendor). Item 1 changes which tools are reported as present, per the list under item 1. Item 3 changes nothing on WSL under option (a). Item 6 changes timing and timed-out output, and the output of a successful capture in the late-descendant case; a user sees most of it as a probe that no longer hangs, and that case as a fact that can go missing from a probe that used to wait for it. For every listed difference the PR either adds a scenario that exercises it in `tests/e2e-cucumber/features/` or states why none can: the empty-entry and non-UTF-8 cases can be driven from a scenario that sets `PATH` and plants a file in the working directory, whereas the Windows candidate spellings cannot run on the Linux lane and need the injectable-function unit test on the Windows job (UNCONFIRMED that the harness can set a non-UTF-8 `PATH`; if it cannot, the PR says so).

## What this note leaves open

- How NVIDIA adapters are represented once the examination reads the inventory (a vendor on every row, or a separate check).
- Whether one `rocm examine --json` run shares answers between the stacks (a single WSL summary and a single `ldconfig -p`, one inventory including its failure) or keeps calling shared code that asks again.
- What an absent Windows inventory does once there is one inventory: remember the absence for the run, or drop the per-fact fallbacks.
- Whether `gpus[].name` should come from `pnputil` or from WMI.
- Whether `kernel_release` should be filled on Windows (the kernel timeout is decided, see "Kernel version"; the CPU read took one 5 s limit, see "CPU model").
- Whether the typed outcome belongs on `CommandCapture` or beside it.
- Whether CPU facts should be collected on WSL at all (option (b) under "CPU model", which the CPU-model change did not take), and if so how the Windows-hosted distro probe obtains them. Scenario `examine-47` and `on_wsl_the_summary_reads_the_cpu_and_the_examination_does_not` pin the empty WSL fields until it is decided.
- Whether the Windows reads should be given more or less time than 5 s once they can be measured on a host, and whether the examination should reuse the summary's inventory instead of running the query itself (the CPU read is still one query per stack).
- Whether the adapters over `run_with_timeout` take a per-call drain grace, so that a probe whose tool is known to leave a late-writing descendant keeps its output, or whether the 200 ms grace is accepted for every probe.
- Whether the near copy of `tool_path_candidates` in `apps/rocm` joins the PATH lookup change.
- Whether the runners that replace the subprocess helpers should refuse to resolve a bare program name through an empty `PATH` entry, so that what the lookup calls absent is also what they do not start.
